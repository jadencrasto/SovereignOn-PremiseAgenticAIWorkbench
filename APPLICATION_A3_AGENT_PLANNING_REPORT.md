## Existing pipeline and findings

Inspected `backend/agent/engine.py`, `planner.py`, `plan_validator.py`, `memory.py`, `task.py`, `task_store.py`, `backend/tools/registry.py`, `calculator.py`, `document_search.py`, `backend/api/chat.py`, relevant task/approval and public-result presentation code, `frontend/src/components/chat/ChatView.tsx` and chat API tests, `APPLICATION_A2_CONVERSATIONAL_AI_REPORT.md`, and the existing application/security baseline. The established path routes suitable requests through `AgentPlanner` -> `PlanValidator` -> `TaskManager` -> `ToolRegistry`, with RBAC, approval and execution gates. Source/task revalidation intentionally blocks approval resume.

The planner previously silently converted malformed model plans into reasoning-only plans and truncated excessive steps; plan validation skipped Pydantic validation entirely when arguments were empty. The calculator plan path could ask the model to rewrite expressions based on earlier observations, without an explicit dependency contract. Calculator `success` was not independently checked before a dependent step. The direct arithmetic shortcut emitted calculator tool events even though it directly called the deterministic evaluator rather than the registry. Blocked `document_search` could return an empty list and be reported as a successful search. Task completion used a stale in-memory plan for step counts, and interruption could leave a task apparently executing. A task terminal event also caused the UI to end its generation state before the stream's final event.

## Changes

- Existing planning heuristic recognizes a calculate-then request, while the existing model/provider planner chooses tools and proposes JSON. Malformed, empty, oversized or structurally invalid plans fail instead of silently becoming reasoning-only or being truncated. Tool schemas validate even empty argument dictionaries. Unregistered and disabled tools remain rejected.
- Added the narrow calculator reference syntax `@step_1.result`. The validator permits references only to earlier calculator steps. The engine resolves them from actual successful, checked outputs of this execution; it does not ask the model to invent intermediate numeric expressions. Before reusing a calculator output, the engine validates its structure, expression, numeric type and result against the existing safe evaluator. A failure stops subsequent steps. This is not a general dependency engine.
- The actual registry and its existing authorization and approval checks remain authoritative; model plans do not grant permissions. Blocked document search now fails before the tool executes, and the planned workflow presents a safe unavailable message. Approval-required synthetic operations pause; task resume remains blocked by existing source revalidation policy.
- Planning execution reads persisted step states before completing, does not declare success with incomplete steps, delays the generated completion summary until the task has transitioned to completed, and marks an interrupted active task `failed_interrupted` without asserting side effects were undone. The planner SSE wrapper closes its engine iterator. No automatic operation retry was introduced. This does not provide idempotency across separate user submissions or a trustworthy exactly-once guarantee after crashes.
- Direct deterministic arithmetic emits text and completion only; it no longer claims that a registry tool ran. The frontend waits for the stream terminal event before clearing the generation state on task lifecycle events.

## A3.2 continuation — PARTIAL (2026-11-13)

### Architecture and dependency contract

Extended the existing `AgentPlanner`, `PlanValidator`, `AgentEngine`, `ToolRegistry`, `TaskManager` and TaskStore; no second workflow executor was added. An optional `bindings` field on each plan step maps an argument name to `{"step_id":"step_1","field":"result"}`. Step IDs remain server-assigned in plan order. Plan validation requires each binding to refer to an earlier step and a declared result field, disallows a literal argument and binding for the same destination, rejects missing/forward/cyclic references and prevents plan transformations from pruning or reordering bound steps. Bound workflows are restricted to enabled read-only tools with server-declared result schemas and verification functions; approval-required, write, unknown, unverified, and reasoning-only steps cannot participate. Runtime accepts only bounded scalar values from an earlier completed step of the same execution and revalidates the fully substituted target arguments. The existing `@step_1.result` calculator expression syntax remains supported.

`ToolDefinition` now supports optional server-owned `result_schema` and `result_verifier` declarations. Calculator registration supplies a strict result schema and re-evaluates the expression to verify the result. An executed step's in-process record carries its step/tool identity, success, validated result, and `evidence_verified` flag; only this record plus the persisted completed step state can satisfy a binding. These records are not durable protected receipts and do not provide independent freshness or exactly-once guarantees. In the current production registration, calculator is the declared verified source. A second read-only tool with an explicit output schema and verifier was registered only in tests to exercise generic bindings; it is not a new product tool. Other legacy tool workflows are not converted into verified workflows by this change.

No automatic retry policy was added: permitted tools execute at most once per attempted step in the tested run. The existing interrupted-task behavior reports `failed_interrupted` with outcomes requiring review; it does not establish whether a side effect occurred or make repeated user submissions idempotent. A synthetic side-effecting tool test confirms interruption after its operation starts is not retried. General side-effect idempotency classification, durable receipts, and restart recovery are not implemented. Approval/resume, document/RAG, artifacts and code-execution security gates remain unchanged.

### Interface

The existing chat UI now records and displays planning, execution, waiting for approval, completion, failure, cancellation and interruption. Interrupted/cancelled workflow labels warn that a started operation may require review. Agent status no longer masquerades as a `tool_start` event. Completion remains described as workflow completion, not independent production verification. The tests drive actual `ChatView` handlers with a deterministic mocked React hook harness; they are not mounted React DOM or browser tests. The local environment did not contain a DOM test dependency, and none was downloaded.

## A3.3 continuation — PARTIAL (2026-11-13)

### Production tool assessment and integration

Reviewed the registrations in `backend/main.py`, `backend/tools/registry.py`, calculator, document search, file list/read/write, artifact verifier, generated-code execution, knowledge graph, hardware telemetry, model scan and security diagnostics, plus the planner/validator/engine paths and chat workflow UI. None was promoted merely because it is labelled read-only.

Added one minimal production capability, `backend/tools/unit_conversion.py`, registered in the normal registry setup through `register_unit_conversion`. It converts bounded finite values among compatible length (`mm`, `cm`, `m`, `km`), mass (`g`, `kg`) and time (`s`, `min`, `h`) units locally. Its typed input/output schemas reject unknown fields, invalid types, incompatible dimensions and non-finite/out-of-range values. A server-owned verifier independently recomputes the conversion using the declared input and checks the output before it can serve as dependency evidence. Its result and target unit have a narrow public presentation allowlist. Calculator remains the other opted-in production tool. No external dependencies or network calls were added.

A synthetic-provider, authenticated in-process production chat route test asks for a calculation followed by conversion. The existing planner chooses calculator, obtains verified `5`, binds it into the real unit-conversion tool, and emits verified `5000.0 m`. A separate tracked tool-loop route verifies an independent conversion and its persisted completed step. This is actual production-module execution with a fake planner, not live model verification or proof that all natural-language formulations select the right tool.

### Alternate paths and interface

The plain tool-enabled loop now requires a provider completion marker, rejects malformed `<tool_call>` markup instead of returning it as an answer, validates opted-in tool outputs, and stops after a failed tool rather than asking the model for an answer that could misrepresent that failure. Successful verified calculator/conversion calls return their checked result directly. The multimodal tool loop received analogous completion, malformed-tag, result-checking and failure-stop guards; it was reviewed and modified but not exercised end-to-end with an image/provider in this batch.

The planned path now rechecks cancellation after its tool-start event and before dispatch. The tracked tool-loop wrapper checks cancellation before resuming its engine iterator, records interruption conservatively, and preserves final persisted step states; a missing tool result cannot be finalized as success. A tool already in flight may still finish after a separate cancellation request: outcomes remain uncertain and no exactly-once or rollback claim is made. Tests cover cancellation immediately before dispatch and existing in-flight interruption cases. The workflow UI adds a readable unit-conversion label and the existing hook-harness tests exercise result presentation, status, approval, failure, cancellation and stale events. React DOM/browser mounting remains unverified; locally available dependencies did not include a DOM test harness and no dependencies were downloaded.
