# R6.4 — Durable conversation provenance

**R6.4: BLOCKED for durable restart recovery; scoped process-local integrity fix implemented. Production: NO-GO.** Starting branch `main`, HEAD `2b96fee1f24777247f4efb7a18293eef4275e9cb`. Prior uncommitted work was retained.

Conversation messages are stored in the locked, atomically replaced JSON conversation store, while the separate conversation registry and task store use SQLite. For independent plain chat, `ConversationMemory` generates a random 32-byte HMAC key on each instance; the v1 MAC authenticates conversation ID, owner, conversation generation and text. Role is checked separately by the verifier. It does not authenticate message ID, timestamp, status or request ID. A new instance has a different key, so prior process-local proofs cannot verify and history withholds their content. The MAC provides no confidentiality, rollback protection or protection from compromise of the running process or its key. Ownership and session authorization remain separately enforced.

**Confirmed issue and scoped correction:** an R6.3 interrupted message used the v1 text-only MAC while `response_state_v1` was outside the MAC. In `backend/agent/memory.py`, newly recorded independently authenticated incomplete messages now use a domain-separated, process-local HMAC-SHA-256 v2 over the owner, conversation ID and generation, message ID, role, content, timestamp and interrupted/failed status. Missing, changed or unsupported state fails verification for that v2 proof; incomplete messages remain excluded from later model context. No key is written to disk and no historical record is re-signed. Existing v1 records retain their previous limitations: their status, message ID and timestamp were not authenticated, and a modified or stripped status on an older v1 record cannot be detected by that proof. Source-derived provenance has separate existing checks and is not upgraded here. The history API still exposes a status field separately from content authorization; it is not a durable cryptographic attestation of status.

**Durability decision:** no reviewed production durable key provider is available. The R4 shared protected-storage writer remains unconditionally unavailable; the experimental Windows broker and native identity/writer exclusion are unverified. The repository inspection did not establish a verified DPAPI/keyring integration or an operator-provisioned secret with a verified protection and recovery boundary. A file path, ordinary ACL assumption or a configuration flag cannot substitute for that evidence. Therefore no durable secret storage, environment-variable fallback, durable signing format, key rotation or migration was implemented. The smallest missing primitive is an independently reviewed provision/load interface that protects a stable key against unauthorized reads and replacement and identifies the authorized backend principal and key version, with explicit key-loss and rotation behavior. Its provisioning and native enforcement require an authorized operator and security verification. This is a technical blocker, not evidence that a key has been provisioned.

The intended future durable record must authenticate a version and key ID, owner, conversation and generation, message ID, role, content, status, ordering/timestamps and relevant operation identity using a reviewed established MAC. It must verify ownership independently and must not silently authenticate legacy records. Backup/restore must preserve the authorized key and matching data; missing, wrong, corrupt or retired keys must leave records retained but unreadable. Multiprocess key access, rollback, rotation, key replacement and future organizational separation require separate design and verification. Current keys are per process; no durable backup/rotation or multiprocess provenance interoperability exists.
