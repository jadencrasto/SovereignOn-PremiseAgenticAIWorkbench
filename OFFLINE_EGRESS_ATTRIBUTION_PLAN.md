## Recommended boundary and monitor

Use a separately approved disposable Windows guest, not the laptop host. Preserve the existing clean baseline; create a distinct pre-instrumentation snapshot only after explicit operator approval. At the hypervisor, independently verify all guest adapters absent/disconnected and no shared folder, clipboard, drag-and-drop, USB or other host communication. Confirm no bridged/NAT/host-only/virtual interface or unexpected proxy route is available; distinguish the guest loopback interface from external connectivity. An adapter-disabled state is a physical/virtual boundary, not a complete log of attempts.

Inside the disposable guest, after separate approval for **guest-only** changes, provision a reviewed default-deny outbound WFP/Windows Defender Firewall policy for IPv4 and IPv6. Capture effective profile/rules, explicit allow rules, rule precedence, policy source and any VPN/proxy/tunnel or existing exceptions. No blanket allow, unrestricted local proxy, host access, DNS or telemetry exception. Only explicitly needed synthetic guest loopback flows may be allowed, and Windows loopback filtering behavior must be demonstrated for that exact configuration rather than assumed. The no-adapter hypervisor boundary remains in force even if the guest policy is misconfigured. If this guest edition, WFP providers, policy precedence or effective rule behavior cannot meet and demonstrate these conditions, stop; use another independently provisioned isolated environment.

Use Windows Security audit **Filtering Platform Connection**, especially event **5157** for WFP-blocked connections and, when explicitly justified, 5156 for allowed connections. Microsoft documents that 5157 includes process ID, application image, direction, addresses, ports and protocol; WFP logging must be explicitly enabled and validated. Successful application requests, WFP allowed events and blocked 5157 events are distinct outcomes. A 5157 indicates a WFP block, not successful transmission; an allowed event does not by itself establish successful application-layer delivery. Local synthetic test logs can contain image paths and addresses; do not collect payloads or secrets. [Microsoft: Audit Filtering Platform Connection](https://learn.microsoft.com/en-us/windows/security/threat-protection/auditing/audit-filtering-platform-connection); [event 5157](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-5157).

For blind-spot investigation, an independently reviewed bounded `pktmon` trace may supplement—not replace—WFP events. Packet drop auditing (5152) is higher-volume and at packet level; capture only synthetic data and stop when bounded space/time limits are reached. `pktmon` can detect packet drops but does not guarantee process attribution or observation of socket calls that fail before packet creation. No packet capture proves zero attempts. [Microsoft: Pktmon](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/pktmon); [packet-drop auditing](https://learn.microsoft.com/en-us/windows/security/threat-protection/auditing/audit-filtering-platform-packet-drop).

Independently review inherited policies, log capacity/retention, privileges, locale and WFP coverage. The current VM and host remain unchanged until then. 2. Record current snapshot identity, guest build, clock/timezone, policy and audit settings. Review the proposed guest-only configuration with a security administrator. As read-only starting checks in the approved guest, `Get-NetFirewallProfile | Select-Object Name,Enabled,DefaultOutboundAction` and `auditpol /get /subcategory:"Filtering Platform Connection"` show some configuration, not the full effective policy or proof of enforcement. No command in this document is a permission to change policy. Windows Home support, audit privileges and event availability must be verified; if unavailable, use a supported disposable guest, not a host workaround.
3. Establish default deny for both address families using a separately reviewed configuration; validate rule precedence and exceptions. Test locally installed monitoring and sufficient log capacity. Confirm a controlled, generated **sentinel attempt** is logged with expected PID/image, timestamp, destination and protocol, with no actual external path. Such calibration needs a separately approved isolated test endpoint/route and explicit safety review. A no-adapter VM can fail with no route before WFP, so a missing 5157 is **inconclusive** and must not trigger a real external request or enabling networking. If independent effective denial plus monitor calibration cannot be established, network-sensitive tests remain BLOCKED.
4. Deliberately verify the independently reviewed loopback-only policy using a synthetic guest-local server if required. No host-bound Ollama, model pulls, DNS, external sockets or production assets. Verify that allowed loopback is not a relay. Include DNS and non-TCP/UDP blind spots; raw sockets, other protocols, children, network-before-process-start, blocked calls before WFP and log loss may escape chosen instrumentation.
5. Before each test start an operator-held time window and process lineage record. An event's PID can be reused; correlate PID, process creation time, executable hash and parent process against a separately recorded process timeline. Event image paths may be sensitive; disclose only sanitized categories. Record dropped/overwritten log counts and monitor state before/after. Timeouts, missing process data or incomplete collection make the outcome inconclusive.

## Evidence and rollback

Minimum observation: `run_id | UTC timestamp and time source | parent/child PID + creation time | executable identity/hash | source/destination address and port | protocol | direction | event ID/filter ID | blocked/allowed/local failure | test phase | monitor-health/loss | sanitized notes`. DNS hostname may be unavailable or differ from destination IP; do not infer URL, payload, remote receipt or library call stack from an event. If no event appears, record `NOT OBSERVED / COVERAGE UNKNOWN`, never `zero attempts` without validated coverage. Unexpected non-loopback attempts, unreviewed child process, changed policy, collector failure, unexpected allowed event or possible actual egress: stop the run, preserve evidence and require incident review.

Photograph the sanitized VM console and event fields before restoration; optionally preserve encrypted/restricted logs on the VM snapshot only if independently authorized, with integrity hashes and a retention plan. No shared folders, clipboard, network, USB or automatic host transfer. Screenshots are operator-observed evidence, not cryptographic provenance. Then power off and restore the **new, reviewed pre-instrumentation snapshot** by operator action; verify that guest audit/firewall changes and synthetic data reverted and baseline snapshot is retained. VM snapshot rollback does not revert host state, exported evidence or external changes and is not proof of forensic preservation. Any incident requiring durable evidence takes precedence over deleting or reverting it, under the approved response procedure.
