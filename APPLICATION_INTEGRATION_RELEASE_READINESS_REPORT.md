## Async stall investigation

Minimal process: `python -c "import asyncio,faulthandler,sys; faulthandler.dump_traceback_later(3, exit=True); print('before asyncio.run',flush=True); asyncio.run(asyncio.sleep(0)); print('after asyncio.run',flush=True); faulthandler.cancel_dump_traceback_later()"` — **timed out after 3 seconds, exit 1 by diagnostic timer**. Python 3.13 traceback shows Windows proactor loop construction blocked in `socket._fallback_socketpair` → `accept`, while creating the event-loop self-pipe; `after asyncio.run` was never printed. This occurs before the coroutine, pending tasks, generators, HTTPX teardown or a database transaction exist. It does not identify why the prior combined A8.2 run stalled, prove a Python/application defect, or explain network/OS policy. No normal event-loop completion was established. The selected fake-provider integration tests use the existing timer-only `TimerLoop` (socket creation forbidden, no cross-thread I/O) or `immediate` driver, which cannot validate real I/O loop lifecycle or executor shutdown. No bypass of isolation or production loop change was introduced. Investigate socketpair behavior and full async cleanup only in an approved, bounded environment.
