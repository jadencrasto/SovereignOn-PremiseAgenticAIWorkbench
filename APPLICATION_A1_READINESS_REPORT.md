# A1 readiness and capability status — partial, not release-ready

Production remains **NO-GO**. This work builds on an interrupted, uncommitted A1 implementation and preserves the existing security gates. No application, model, VM, Chroma, or service was started for this verification.

## API and interface

`GET /api/health/capabilities` is passive. It returns schema version 1, environment, an unverified deployment indicator, capability states (`available`, `unavailable`, `blocked`, `unknown`), configured models and an optional recently observed inventory. Backend readiness means application startup completed; it does not certify deployment security. Persistence initialization does not prove durability. Model inventory is not inference verification: chat, planning and multimodal remain unknown when their model prerequisites are merely listed. Document/RAG, approval/resume, artifact access and generated-code execution remain blocked.

`POST /api/health/capabilities/ollama-check` requires the existing view permission, is explicitly invoked, uses a time and response-size limit, disables proxies and redirects, and accepts only a validated HTTP loopback target. Results expire after 60 seconds. No check is triggered at import or by passive polling. The explicit check is a local network request when the user invokes it; no such request was made during this work.

The interface displays capability states and reasons, presents blocked document and artifact screens as unavailable, and reports unverified deployment. Existing security gates remain authoritative. The status bar now displays the RAG state instead of incorrectly implying an empty index. Browser interaction and all presentation paths have not been independently tested.

## Launcher

`scripts/dev.ps1` checks selected dependencies, requires the default loopback backend configuration, refuses occupied ports, checks both HTTP responses with a deadline, and stops only the PowerShell jobs it created. It does not install or pull models. **Its ownership and child-process cleanup behavior has not been tested**; the Python reload process and npm may create children. Port checks and subsequent binds have a race, and an unrelated process could bind between them. Do not treat this launcher as verified isolation or reliable cleanup until those cases have been tested. It checks selected imports, not a complete dependency manifest or installed models.

## Launcher ownership investigation — BLOCKED

The prior invocation used Windows PowerShell `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` (version 5.1.26100.9818), whereas the current command shell is PowerShell 7.6.9. The latter reports MachinePolicy and UserPolicy undefined, Process and CurrentUser undefined, and LocalMachine/effective policy `RemoteSigned`. The test script and launcher both report `NotSigned`, and their alternate-stream listings showed only `:$DATA`, with no `Zone.Identifier` Mark-of-the-Web stream. An unsigned local file's signature status alone does not establish why `RemoteSigned` would reject it.

In this managed environment, the actual Windows PowerShell 5.1 process reported `Requested registry access is not allowed` when reading CurrentUser execution policy; its LocalMachine scope reported `Undefined` and Process scope `Undefined`. This is strong evidence of an environment-specific policy-read problem, but it does **not** establish conclusively that this caused the previous `AuthorizationManager check failed`, nor does it establish the host's complete policy outside this environment. The previous test did not run. No policy, file trust, registry, firewall, or security settings were changed, and no policy bypass was attempted.

Static inspection found that `Start-Job` plus `Stop-Job` does not establish ownership or cleanup of Python reload and npm descendants. Port availability checks also race subsequent binding, and HTTP replies alone do not identify the listener. Killing by port or guessed parent PID would risk unrelated processes. The old launcher cannot demonstrate the requested ownership guarantees.

The requested process startup, descendant cleanup, unrelated-process preservation, dependency failure, occupied-port, partial-startup, normal-shutdown, and timeout tests are **BLOCKED / not executed**, not passes.
