# I10 artifact integrity

**I10: PARTIAL. Production: NO-GO.** Existing artifact-producing registry paths now fail closed until execution-bound verification exists. This deliberately blocks `docx_create`, `xlsx_report` and `file_write` at registry dispatch; it does not enable protected generation or publication. Tool inventory can still describe these registered tools as enabled even though dispatch is blocked; availability presentation remains to be reconciled.

## Existing architecture and defect

DOCX/XLSX generators create exclusive opaque files and return filename, artifact ID and self-computed digest. The registry previously treated any normal handler return as a successful tool result and could register artifact metadata without independent structural verification. A filename, self-reported digest, or TaskStore row does not establish ownership, provenance, verification or publication. PDF generation and the A7 verifier are isolated and not registered as production tools. The agent has a source-grounding precheck, task status tracking, I8 registration checks, I8.1 request-bound identity refresh and registry approval checks; document provenance and approval resume remain blocked. Artifact preview/download use a separate provenance gate which currently denies even admins.

## Changes and boundaries

After existing owner, approval-verification, RBAC and argument checks, `ToolRegistry.execute` now denies those three artifact-producing names before invoking the handler or consuming approval. This prevents their unverified return values from causing a successful registry result or TaskStore artifact registration, including direct registry entry. Missing owner or approval is still rejected by existing checks. This is a restrictive stopgap, not verify-before-success integration: it also disables otherwise legitimate `file_write` operations, and arbitrary future tool names would require their own classification. Direct calls to generator functions remain internal and are not covered by the registry guard. No approved production execution path can currently return a verified artifact: trusted source authorization, execution-bound staging/ownership, approval and recovery are not established.

The isolated existing verifier now independently checks written PDF body and table lines as well as headings and source references; its earlier post-write check could accept a structurally valid PDF containing only headings and sources. The XLSX verifier now rejects formulas in the title and notes cells in addition to table cells. Verification continues to return `verified_unpublished` checked bytes, which is neither a task receipt nor publication authority. Tests generate and reopen synthetic DOCX, XLSX and PDF, check expected content, digest and formula handling, reject missing PDF body and an XLSX formula title, reject corrupt DOCX/digest mismatch, and preserve unknown orphan files. PDF text extraction is not visual-layout verification. Real file tests use private temporary directories, not production storage.

The registry tests supply synthetic owner/approval context and fake handlers that would claim success without files: the actual registry denies invocation, does not consume approval and does not save artifact metadata for all three names. Existing tests separately cover missing owner/approval, protected-source planning failure and blocked resume; artifact access is withheld by existing public guards and frontend controls. The tests do not prove task-bound successful verification, secure publication, all corrupt XLSX/PDF cases, durable cross-owner access controls, process crash recovery or cross-process authorization ordering. After a real side effect starts, cancellation does not prove rollback; unknown leftovers remain quarantined and no retry or recovery promotion was added.
