# Network-sensitive test gate matrix

## Current implementation guard

`tools/offline_verification/network_sensitive_test_runner.ps1` unconditionally refuses all execution, including when purported approval or synthetic calibration evidence exists. It does not intercept direct pytest or other process launches; organizational and OS controls remain necessary. Native collector/calibration, safe durable evidence, independent isolation and approval are unverified, so none of the commands below may be enabled through this prototype.

**All network-sensitive execution is NOT RUN and NOT APPROVED by this documentation task.** The commands below are exact *proposed candidates*, not currently approved actions. No host networking or host firewall changes; no VM startup or test execution occurred. Do not retry the automatically rejected full-suite attempt without the applicable independent review decision. Production NO-GO.

## Common gates for every row

1. Explicit separate owner/security approval of the isolated VM, exact command, data, process tree, loopback requirements and evidence retention. The VM's guest-only instrumentation/policy changes require their own approval; no host security changes.
2. Hypervisor isolation verified independently: no adapters or other egress/host channels. Snapshot and rollback reviewed. Effective guest default deny and monitor calibrated for the specified protocols, IPv4/IPv6 and child processes. Unknown coverage or a no-route-with-no-event result is **not a pass**.
3. Reviewed exact offline dependencies and hashes, no package downloads, no production data or credentials, fresh synthetic temporary paths, bounded duration and process cleanup. Confirm pytest collection hooks and plugin list by **static inspection**, not collection execution, before running. Disable external pytest plugin autoload; explicitly enable only reviewed required plugins. Confirm Python interpreter, startup/site hooks, proxy configuration and test-specific filesystem destinations. A flag alone is not isolation.
4. Capture start/stop times, PID lineage, event data and monitor health; distinguish blocked attempts, allowed connections and pre-WFP local failures. Stop on unexpected attempts or unknown behavior. Retain/photograph sanitized results before snapshot rollback.

## Operational rules

When a 5157 is observed, record it as a WFP-blocked connection, not successful egress. WFP 5156, a socket success, or a loopback request do not establish external transmission. Failure before routing/WFP can yield no audit event, and no adapter alone does not attribute attempts. If visibility is insufficient, retain UNKNOWN and do not expand tests. Guest-only policy changes must be reversible through an approved fresh snapshot; preserve sanitized evidence first. See `OFFLINE_EGRESS_ATTRIBUTION_PLAN.md` for calibration, limitations and rollback.
