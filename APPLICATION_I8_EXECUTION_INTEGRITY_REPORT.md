# I8 execution integrity

**I8: PARTIAL. Production: NO-GO.** The changes protect selected in-process planning/dispatch handoffs; they do not establish fresh account authorization, immutable execution across processes, or durable concurrency guarantees.

## Architecture and changes

The production planner returns an `AgentPlan`; `PlanValidator` validates it and applies approval requirements; `AgentEngine` persists and executes its steps via `ToolRegistry`, while `TaskManager` persists states. The registry enforces its existing RBAC, approval, capability and input checks; verified read-only results may feed dependencies. Chat authenticates the request before passing the identity and role into the stream.

Two concrete risks were addressed:

* The engine previously retained the planner's mutable object. It now deep-copies the entire plan before validation and executes the detached copy. The test changes the planner's original arguments and tool name after `plan_created`, and observes the original calculation. Execution still mutates its private copy for statuses and validated dependency binding; this is a defensive snapshot, not a formally immutable plan or cross-process tamper-proof record.
* Registry entries were mutable and could be replaced between validation and dispatch. A process-local token now covers the registration generation, definition/handler/schema/verifier identity, schema representations and execution-relevant metadata. The planned path captures tokens before validation, checks them after approval enforcement, passes the expected token to registry dispatch, and rejects changed registrations before invocation. It also refuses to verify a result against a changed registration. Register, unregister, enable and disable invalidate old tokens. Direct and resumed dispatch are not bound to a plan token by this change. Schema internals, in-place change-and-revert, concurrent threads between the last check and call, and cross-process changes are not comprehensively synchronized; this is not a durable receipt or an atomic global execution lock. A registration change after a tool begins cannot undo its effects; the resulting failure says the outcome cannot be verified.

The task manager serializes transitions using its instance lock and rejects invalid terminal transitions. The new test checks that cancellation cannot be overwritten with completion in one manager. Existing focused tests exercise invalid dependencies, pre-dispatch cancellation, approval waiting and interrupted side effects. They do not prove all concurrent completion/cancellation races or independent process synchronization.

## Authorization and remaining gaps

The request dependency checks account activity at authentication, but chat passes the then-current role into a potentially long-lived stream. Dispatch rechecks RBAC against that role and existing approval consumption against the operation; it does **not** independently refresh account status or role for every new dispatch. Role revocation and account-disable races therefore remain unverified and may permit use of stale authority. No durable authorization-freshness mechanism was invented. Existing owner, provenance and blocked approval-resume boundaries are unchanged; current tests do not establish all cross-owner race guarantees. Future work must establish authoritative identity/session freshness at dispatch and explicit in-flight revocation semantics, then add controlled revocation and cross-process tests. No new frontend event category was introduced; existing failure handling is used.
