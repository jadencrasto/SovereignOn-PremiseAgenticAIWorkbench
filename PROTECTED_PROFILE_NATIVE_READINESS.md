# Protected-profile native readiness

**Decision: BLOCKED for the full Protected profile. Production remains NO-GO.** The repository contains an observation-only service fixture and native inspection scripts, but the required independently reviewed Protected provisioning, trust manifest, distinct identities, effective permissions and rollback evidence have not been established in this review. In particular, the broker storage probe needs to run under the actual restricted service token; the existing fixture does not provide a reviewed mechanism to do so. A separate decision may authorize a narrower identity or endpoint observation after its own prerequisites are satisfied; it would not establish the complete storage boundary.

## Evidence and scope

This review inspected repository documents, source and runner scripts and Git status. It did not start or inspect VirtualBox, inspect the guest, execute scripts or tests, verify an ISO, create accounts, alter ACLs, or verify snapshots. Existing tracked and untracked work was preserved. The operator reports Lifecycle Service and synthetic Recovery PASS and a Windows 10 Home isolated VM with retained reusable snapshots; those are operator-reported outcomes, not newly examined console records or independent attestations. The 14 witness-prototype tests are synthetic and do not establish independent freshness.

The previous reports document offline fixture results: 11 K service-fixture cases, 24 L identity cases, 21 M endpoint cases, 27 N storage-policy cases and 33 integration cases. These are historical reported results, not tests run in this review and not evidence of native Windows enforcement. The protected native identity, endpoint and ACL outcomes remain unverified. The separate egress calibration is BLOCKED; network-sensitive application tests remain blocked.

## Identities, ACLs and expected outcomes

Provisioning would be a separate, privileged guest-only operation requiring approval. It must specify the nonadministrator broker logon identity, restricted service SID, non-elevated observer/application identity, a different non-elevated independent identity, administrative provisioning authority, required group membership, service-logon right, process/token query permissions and a procedure for checking effective rights. The Protected fixture should run as a dedicated own-process service. No passwords or keys belong in the manifest or test output.

The reviewed K descriptor gives the broker user and service SID mask `0x0012019F`, and the observer `0x00120081` for read/attribute access, `READ_CONTROL` and synchronization; the observer mask excludes client pipe-instance creation. No broad Everyone access is implied. A different unauthorized identity should be denied. The pipe is outbound-only and accepts no application requests. It retains one handle for one observation, with a 30-second connection wait and a bounded worker lifetime; a second observation needs a fixture restart. Name squatting before startup and after exit, plus cross-process races, still require native review. First-instance creation and an observed matching PID do not authenticate the server.

For `synthetic-storage-k`, the reported fixture comprises an empty `.synthetic-only` marker, `document.fixture`, `sqlite.fixture`, `vector.fixture`, `artifact.fixture`, `audit.fixture`, `recovery.fixture`, `witness.fixture`, and a sidecar directory with WAL/SHM fixtures. Application and independent users should be denied mutation of the fixtures and their parents. The restricted broker is expected to have only reviewed synthetic-store mutation and sidecar-create rights, append-only audit access, and no witness mutation; parent replacement, delete-child, ACL and owner changes remain denied. Metadata and read permissions must be sufficient for the actual probes without granting unintended mutation. Validate effective rights, inherited ACEs, reparse points, hard links, pre-existing handles and privileged bypass separately; an ACL description alone is not proof.

The probe does not prove complete writer exclusion, enumerate all inherited handles or mappings, validate a separately administered witness, test all backup/recovery privileges, or authenticate request-capable caller impersonation. The K fixture does not implement a request-capable channel. Production access and authorization remain disabled.

## Windows 10 Home compatibility

The reported edition is not itself proof either that the underlying SCM/token APIs are unavailable or that the complete fixture can be provisioned. Microsoft documents that `SERVICE_SID_TYPE_RESTRICTED` adds the service SID to the process token's restricted SID list, and describes restricted-token access checks: [SERVICE_SID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_sid_info), [Restricted Tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens). Microsoft also documents local-account management through command-line and PowerShell mechanisms on Windows clients: [Local accounts](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/local-accounts). Availability of the Home edition's local-user/group and policy management interfaces can differ; Microsoft's support discussion notes that the Local Users and Groups snap-in is unavailable on Windows 10 Home: [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/3318199/users-groups-is-not-available).

Before provisioning, a reviewer must establish the exact guest build and whether the approved methods can configure the service logon right, service SID type, protected NTFS ACLs, SCM security and cross-account token inspection on that installation. The cited API documentation does not verify this particular VM or its effective rights. If any essential capability cannot be established without changing the security model, stop and use a separately approved compatible disposable VM; do not broaden permissions to compensate.

## Workspace, artifacts and existing snapshots

The packaging source currently lists the K, L/M and N runners, but this review did not inspect the actual operator-used ISO or its inventory. Reuse is conditional on independently verifying that the exact signed package contains the current reviewed scripts, all required .NET artifacts and matching manifest/schema, and on confirming its publisher trust and pinned hashes in the selected snapshot. The operator-reported Lifecycle ISO/launcher values in the evidence ledger are not a substitute for checking the specific Protected package and binary pins. A new ISO is required only if the verified package lacks the needed reviewed artifacts or carries incompatible versions; no rebuild was performed here. Development-certificate trust, .NET and PowerShell installations may be reused only if actually present and reviewed in the chosen snapshot; they do not make service identity or the manifest independently trusted.

The setup script uses a fixed workspace, `C:\SovereignVmVerification`, and refuses an existing `batch2b3o.json`; Protected requires its own pinned manifest and profile. Do not overwrite the Lifecycle configuration, marker or files or assume an alternate workspace is accepted. Select an independently reviewed clean/base snapshot with a safe staging state, or design and review a separate supported staging procedure before provisioning. Preserve the Lifecycle and baseline snapshots. A snapshot label entered into the script is an operator assertion, not a verification of snapshot existence or restoration.

## Safe work without the VM

Read-only source and documentation inspection can proceed on the host. Previously reported offline self-tests for service-fixture, identity, endpoint and storage logic, and PowerShell parser checks are candidates for future host execution after reviewing their present imports, files, temporary writes and exact commands. No tests or builds were run now. These checks cannot establish actual Windows ACL enforcement, cross-account access, restricted tokens or SCM behavior. The egress-monitoring gate continues to block network-sensitive application tests; a narrowly reviewed local-only identity/ACL fixture would need its own explicit scope and approval, not a blanket exception for application integration tests.

## Required approvals and shortest safe route

**There is no authorized Protected execution sequence while this decision is BLOCKED.** To make a limited run eligible for a new readiness decision:

1. Confirm and document the exact isolated guest, edition/build, disconnected adapters and disabled integration channels, retained snapshots and a separately approved, recoverable pre-provisioning snapshot. Define evidence preservation before any reversion and verify rollback after it.
2. Independently review the Protected account/token, SCM security, pipe descriptor, protected installation, synthetic NTFS ACL and fixed-service conflict procedures. Obtain explicit approval for guest-only account creation, privilege assignment, service registration/start/stop and ACL changes. None is authorized by Lifecycle approval or this report.
3. Resolve the restricted-service-token probe-host gap and review the exact bounded test and cleanup implementation before claiming broker storage verification. Separately review fixtures for distinct-SID denial, existing handles, replacement, privilege bypass and independent witness behavior; unsupported cases remain open.
4. Independently approve the manifest and its digest, exact artifact hashes and package contents; select a safe separate Protected configuration without overwriting Lifecycle files. Check Home compatibility and cross-account inspection rights without weakening security.
5. Reassess readiness and explicitly approve each limited native run. Capture sanitized console evidence and cleanup status before restoring the approved snapshot; stop on failed, ambiguous or incomplete cleanup. Snapshot restoration is the complete rollback, not a claim that deleting a service reverses all provisioning.

If a narrower identity/endpoint-only run is later approved, start the preprovisioned fixture through the reviewed guest procedure, run the pinned observer within its documented connection window, record the categorical result and stop/restore according to that approval. Repeat negative observations only with independently selected identities and separate fixture restarts. Do not start FastAPI, Chroma, Ollama or other network-sensitive tests as part of this limited scope.
