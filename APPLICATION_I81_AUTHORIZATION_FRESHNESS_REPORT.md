# I8.1 dispatch-time authorization freshness

**I8.1: PARTIAL. Overall I8: PARTIAL. Production: NO-GO.** A fresh identity decision now protects the existing agent dispatch boundary, but atomic cross-process revocation versus invocation and the complete approval-race matrix remain unverified.

## Capture points and implementation

`get_current_user` originally validated the session and account once and chat passed its role and user ID into the streaming engine. Registry RBAC then used that potentially stale role. Conversation generation/ownership, task identity, registry identity, capability gates and approval verification have separate existing checks.

Successful server authentication now binds a request-scoped resolver to the same session manager, account store, token and server-derived user ID. Before **each** agent `_dispatch_tool`, the resolver revalidates the session and reloads the active account; the engine checks the resolved ID against the request owner, rechecks the conversation identity, and, for a task, checks its owner and conversation. The current role replaces the captured role for the existing registry RBAC decision and the current clearance is scoped to that invocation. Exceptions, missing resolver, session/account failures, unknown roles or ownership mismatch deny dispatch with a generic failure; the registry continues to enforce arguments, capabilities, approvals and I8 planned-registration tokens. The resolver is reset at request middleware exit. It retains the credential only in the request-scoped closure and does not log it. Session revalidation uses the existing sliding-idle `validate_session` behavior.

The established unauthenticated local-development admin can be resolved only while that server configuration remains non-production and authentication remains disabled. Header-selected development role simulations do not receive dispatch authority. Direct engine callers without a server-bound resolver now fail closed; older synthetic test helpers were updated to supply an explicit test-only principal. No client role or clearance is accepted as fresh authority. Non-agent direct calls to `ToolRegistry.execute` are outside this new engine boundary and still require their own authorization review.

## Ordering, task and approval limits

The decision observes a valid session followed by an active account and role, then checks conversation/task ownership before registry policy and invocation. These reads are **not one atomic snapshot**: revocation, role change, cancellation, ownership change or registration mutation may race after its respective check, including across processes. There is no durable revision or transaction tying revocation to invocation; the last relevant read is an observation, not an atomic cross-process linearization point. No lock is held across tool execution. Effects of a tool already dispatched may be uncertain and are not rolled back or retried. I8's process-local registration token remains limited in the same way documented there.

Before-dispatch denials flow through the existing failed-tool / failed-task events; cancellation retains the existing cancelled outcome. Previously completed verified steps are not rewritten. The generic message avoids exposing identity details, so the UI does not distinguish account, session and role denial categories. No frontend change was made. Approval verification and one-use consumption remain in the registry; blocked resume stays blocked. A mocked invalid approval and wrong-owner request were denied, but approval invalidation after issuance, changed arguments/other approver ownership and cross-process approval races were not comprehensively retested under live authenticated streams.
