## Changes

- Ollama chat and streaming reject malformed responses, unsupported structured tool calls, missing completion, and premature EOF. A total request deadline supplements HTTPX timeouts. HTTP 404, timeout, and connection errors are categorized without publishing raw provider response bodies. HTTP resources remain under async context management and cancellation is not swallowed.
- Plain engine streaming requires a final provider completion marker and nonempty response before storing an assistant response. It retains a short suffix to detect a split `<tool_call` marker; the plain synchronous path also rejects these markers. This is a targeted guard, not a proof that every possible representation of tool syntax is filtered across every agent/planning/multimodal path.
- The plain SSE path surfaces a fixed allowlist of safe provider failure messages. Existing authorization and stream identity guards remain in place.
- Both frontend stream parsers detect malformed and interrupted responses and avoid processing multiple terminal events. Chat callbacks are guarded against late events from a cancelled or replaced generation, and cleanup no longer clears a newer request's controller. Approval UI no longer asserts execution success merely because an approval response ended.
- Added `tests/backend/test_a2_provider_offline.py` and `frontend/tests/a2-stream-client.test.cjs`. Existing uncommitted changes were retained.

## A2.1 continuation — PARTIAL (2026-11-13)

### Root cause and design

Plain chat previously stored `source_provenance(sources)`. Empty retrieval could mean skipped, failed, or timed-out retrieval, so it was deliberately not evidence of independence. `_build_messages` excluded all ordinary assistant responses, while history display withheld responses with unknown provenance. Document authorization remains fail-closed; persisted provenance assertions are not trusted as independent proof.

Added **process-lifetime independent plain-chat proofs** to the existing `ConversationMemory`. An in-memory random HMAC key signs the assistant content together with conversation ID, server-bound owner, and active conversation generation. The key is not persisted. Plain output is signed only if document content is currently blocked, the supplied sources list is empty, the actual provider input consists only of authorized user messages, the configured system prompt, and already verified independent assistant messages, with no image payloads; the conversation identity and document gate are checked again before signing. Deterministic calculator history remains usable under its existing rule, but because it lacks the new proof, a response depending on it is not newly classified as independent. This preserves the prior authorization for calculator context without extending trust to its descendants.

Proof verification is used both for reconstructing provider context and displaying owned conversation history. Invalid, missing, modified, copied across identities or conversations, or old-process proofs are withheld. Proofs deliberately stop verifying after process restart; persisted responses are not promoted merely because their metadata says they are independent. Unknown, document- or tool-derived assistant content is excluded from provider input as before. Document gate and ownership checks remain authoritative. Since no source-bearing assistant response is replayed under the new rule, there is no new source-bearing dependency chain to propagate; source-dependent multi-turn replay remains blocked rather than treated as independent. This design assumes the configured system prompt and server-authenticated user's own messages are permitted model inputs, and does not provide trusted persistent integrity, OS isolation, or verification of model-internal training data.

The engine and plain SSE wrapper now explicitly close their async iterators on generator closure. The non-streaming route uses the existing allowlisted provider errors. The frontend callback guard has been extracted into a directly testable helper and is still used by `ChatView` to suppress callbacks from abandoned generations. No interface redesign or broader tool-path change was made.

## A2.2 continuation — PARTIAL (2026-11-13)

### Durable provenance decision

Durable assistant replay remains blocked. `STORAGE_INTEGRITY_RECOVERY_FOUNDATION_REPORT.md` and `INDEPENDENT_FRESHNESS_ROLLBACK_ASSESSMENT.md` record that current JSON/SQLite locks and atomic replacement coordinate ordinary writes but do not establish protected writer identity, independent authorization freshness, rollback resistance, or cross-store recovery. The existing prototype witness is in the same restore domain and is non-authorizing; no production key-management boundary suitable for durable conversation proofs was found. A persisted HMAC key or locally stored counter would not by itself establish current ownership, revocation, ordering or freshness after coordinated rollback. The process-local key was not persisted. After restart its prior proofs fail closed, and old assistant responses remain withheld. This is a security limitation and a user-visible continuity gap, not evidence that local persistence itself is absent. No new durability authorization system was added.

### Implemented changes

- The chat route's streaming response closes its body iterator in `finally`, while the request authorization context remains in scope. This fixes a synthetic ASGI send-failure case in which the generator had previously been left to asynchronous garbage collection.
- Both frontend SSE readers cancel the readable body and stop reading after a terminal event; an open body no longer leaves the client waiting after `done` or `error`.
- Added timer-only asynchronous provider/deadline tests and an in-process ASGI disconnect simulation. Added a deterministic hook harness that exercises the real `ChatView` function's handlers and state transitions, plus an SSE terminal cleanup regression. No production provenance or authorization gate was changed.
