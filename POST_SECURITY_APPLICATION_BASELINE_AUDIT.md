# Post-security application baseline and development roadmap

## Executive summary

**The application has a substantial backend and interface, but its current working tree is not verified as a complete working product. Production remains NO-GO.** This audit did not start the application, model, Chroma, VM or any tests. It examined the current `phase1-5-recovery-security` working tree, which contains extensive pre-existing tracked and untracked changes. Historical results below relate to the versions and test conditions recorded in their source reports, not a fresh verification of this entire tree.

The shortest useful development path is to make the local experience honest and testable: clearly show which features are unavailable, repair the development startup workflow, then test chat and planning against controlled fake providers. This work can proceed with synthetic data while the Windows protected-service work continues separately. Document retrieval, artifact reads, task approval/resume and generated code execution must remain denied until their own security prerequisites are satisfied. Live model, real Chroma, actual application startup and network-sensitive integration require an independently established monitored isolation boundary and separate approval; the prior automatically rejected full-suite attempt must not be retried without its applicable review authorization.

### Evidence scale

- **Working and verified (scoped):** behavior actually observed in a documented test; dependencies, environment and date are stated. Does not imply a current live-system pass.
- **Implemented, unverified:** source contains a real path, but no adequate current end-to-end evidence was found in this audit.
- **Partial/broken:** concrete limitations or mismatches identified; not necessarily an observed current runtime failure.
- **Security-gated:** intentionally denied. This is a current product limitation, not permission to remove the guard.
- **Not implemented:** missing production capability or verified design.

## Top five highest-impact fixes

1. **Truthful capability and status UI:** remove unsupported guarantees, explain blocked ingestion/retrieval, task resume and artifact access; distinguish unavailable, empty and error. Map existing error codes safely without exposing paths or content.
2. **Reliable development startup:** isolate runtime paths, check actual backend/frontend readiness and terminate only jobs the launcher created. Add an offline preflight that reports missing dependencies or models without pulling/installing anything. Avoid `Get-Job` cleanup of unrelated jobs.
3. **Reproducible, safe chat contract:** fake-provider tests for stream success/error/cancel, server-authenticated session ownership, empty or stale context and model-unavailable behavior; do not assume the full application can be initialized safely on the host.
4. **Agent plan and approval correctness:** deterministic fake-model/tool tests for schema validation, tool permission and blocked approval/resume; surface the limitation in the UI. Preserve all policy gates and avoid executing arbitrary code.
5. **Multimodal and persistence integrity:** independently verify multipart ingress limits, image lifecycle and retention; improve conversation recovery only with owner/revocation controls. Do not promise restoration of sources/artifacts/attachments until provenance is established.

## Prioritized development milestones

Each milestone is suitable for synthetic, non-sensitive development. “Safe tests” are candidate techniques, not commands automatically authorized for network-capable application startup. Review imports, plugins and filesystem paths before running. Use standard-library isolated tests or frontend pure helper tests where feasible; real framework imports and browser runs remain conditional on a separately established monitored default-deny environment. Protected-profile and witness dependencies are specified per milestone; independent egress controls remain a prerequisite to live network-capable tests.

## Recommended first development milestone

Implement **local readiness and honest capability presentation**. It produces a visible improvement without weakening authorization or requiring Protected provisioning. Scope: explicit unavailable messages for document/RAG, task approval/resume and artifact reads; remove unconditional air-gap assertions; fix safe process-owned startup/cleanup and no-download preflight. Use fake process/provider and frontend state tests, then pursue live integration only when the network boundary is approved. Do not treat a capability banner as a substitute for backend enforcement.

## Verification record and release decision

Historical evidence: `FINAL_INTEGRATION_REPORT.md` reports 2 actual-app route tests with fake model/Chroma and 81 selected backend tests in a temporary archive, plus frontend static checks and 4 helper tests; subsequent reports narrow or supersede older findings. `PHASE1_SAFE_HOST_SECURITY_TEST_RESULTS.md` reports 10 stdlib synthetic checks; `STORAGE_INTEGRITY_RECOVERY_FOUNDATION_REPORT.md` reports 8+6+7 selected offline tests. These results overlap in scope and are not summed into a whole-product pass. No tests were run for this audit, so current pass/fail/skip counts are **not measured**.

Production release stays **NO-GO** until the original egress issue and monitoring, actual authorization paths, protected identity/storage, recovery/freshness, and independent release review are addressed. This audit creates only this report; it does not change product source, start services, access the VM or modify existing evidence.
