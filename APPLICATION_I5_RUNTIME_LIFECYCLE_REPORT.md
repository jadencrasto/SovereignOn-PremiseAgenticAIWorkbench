## Implemented foundation

Added `backend/runtime/lifecycle.py`: a **non-wired state-machine prototype**, with no Windows implementation and no sockets, process creation, termination or PID-based operations. Its default `UnavailableDriver` fails closed. A prospective adapter is represented by a protocol and would have to provide containment and stable handles. The coordinator takes a supplied preflight result, starts through that adapter only after `ready` is exactly true, models two roots, a monotonic deadline, health and listener checks, child exit, failure cleanup, repeated stop and a distinct `cleanup_unverified` state. It rechecks ownership and liveness after a health response and does not call health for a listener reported as another process. Diagnostics are bounded categorical state/failure fields and omit paths, environment values and content.

The current real read-only preflight returns `ready: false`; passing a synthetic `{'ready': True}` to the prototype is test input, not authorization, proof of readiness or a trustworthy security boundary. There is no startup integration and no claim this prototype can manage the real application. The driver protocol accepts caller-provided claims; Python objects do not establish OS ownership. Deadlines are checked only when `poll` is called, and driver calls may block indefinitely. A future implementation needs an independently enforced timeout/supervisor and safe handling of adapter failure after native resources are acquired.

## Job Object design to complete before use

A candidate native implementation would create a dedicated Job Object with `KILL_ON_JOB_CLOSE`, create each child suspended, hold non-inheritable job/process handles, assign it to the job before resuming, verify assignment and fail closed if nested-job restrictions or assignment fail. It must safely terminate a created suspended root via its still-open handle on failed assignment, never a recycled PID; reliably close thread/process handles and preserve the job handle for the entire lifetime; deny breakaway and separately evaluate nested-job, broker-created children and inheritance/escape paths. Kill-on-close is not proof that arbitrary brokered/out-of-job work is contained. Graceful termination, forced job termination, confirmation of all members exiting, supervisor crash, external handles and cleanup failures need actual Windows testing. None of this native code exists or was verified in I5.

Listener readiness requires an independently implemented Windows listener-to-process mapping, comparison against a live owned handle/creation identity and Job Object membership, liveness before and after the health response, and an analysis of PID reuse and time-of-check races. The current abstract `listener_state` is only a contract; the in-memory tests do not verify any Windows listener or occupied port. An occupied port must never authorize termination of its owner. A port/HTTP response or adapter boolean alone cannot establish listener ownership.

## Driver and coordinator

Added `backend/runtime/windows_job_driver.py`, a separate experimental ctypes implementation of the existing coordinator adapter, injected explicitly as `RuntimeCoordinator(driver=...)`; the default coordinator remains unavailable and the real preflight remains not ready. No launcher or API was wired to it. No dependency was installed. Existing Windows inspection code was inspected; it did not supply an equivalent Job Object supervisor.

The proposed native path uses `CreateJobObjectW`, `SetInformationJobObject` with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, `CreateProcessW` with `CREATE_SUSPENDED` and no inheritable handles, `AssignProcessToJobObject`, `IsProcessInJob` and `ResumeThread`. Roots are recorded by retained native process handles, not PID-based kill authority. The job has no explicit breakaway-allow flags; nested job assignment may fail and cleanup is intended to fail closed. On failed assignment a still-suspended unassigned process is terminated using its retained process handle. Cleanup uses `TerminateJobObject`, handles for unassigned roots, `QueryInformationJobObject` active-process count and root handle liveness. If termination, status or zero-active evidence is unavailable, it returns false and the coordinator records `CLEANUP_UNVERIFIED`; repeated coordinator stop does not falsely report success. There is no wait/retry for asynchronous job teardown, so a healthy cleanup can be reported uncertain and handles retained. Close failures and recovery/retry need further review. The API and structure declarations are implementation proposals, not validated native interop evidence.

The coordinator's deadline is polled; Windows API calls are not externally bounded by it. Adapter-supplied preflight data and health responses are not an independent authorization boundary. In particular, no protection against hostile processes duplicating job handles, brokered/out-of-job children, job nesting or environmental restrictions is established. Closing a kill-on-close job is not proof that external/broker-created descendants are owned.

## Listener identity

**Not implemented.** `listener_state` always returns `unknown`, and `health_ready` returns false. Thus the coordinator fails readiness and attempts cleanup rather than trusting an HTTP reply or PID. There is no `GetExtendedTcpTable`/IPv6 mapping, live process-handle/creation-time correlation, job membership validation for a listener, listener race mitigation or PID-reuse proof. No unrelated listener is targeted by port. Implement and independently verify those mechanisms before any claim of readiness; a PID lookup plus a response is insufficient. Root-process exit while a descendant remains currently fails the coordinator and triggers job cleanup rather than treating the descendant as ready.

## Resolver and coordinator

Added `backend/runtime/windows_listener.py`. The unverified ctypes bridge proposes `GetExtendedTcpTable` OWNER_PID_LISTENER for IPv4 and IPv6, `OpenProcess` with query-limited/synchronize rights, `GetProcessId`, `GetProcessTimes`, `WaitForSingleObject` and `IsProcessInJob`. Table parsing bounds record counts and buffer length, requires LISTEN state, decodes network-order ports, and matches the exact configured IPv4/IPv6 loopback and port. Both address-family tables are read; wildcard bindings return unknown because wildcard/dual-stack ownership cannot be inferred safely. Scoped IPv6 rows currently make the table unknown; arbitrary addresses, wildcard and dual-stack readiness are unsupported.

`ListenerResolver` takes two table snapshots, opens and temporarily retains a listener process handle, compares its PID and creation time with the existing root's retained process handle, checks both are live and verifies the listener handle's job membership, then rechecks the snapshots, identities, liveness and membership. It returns absent, other, unknown or owned. Duplicate rows, changed table, exited process, access/API errors, close failures and ambiguity fail closed. Expected-root-only correlation intentionally does not establish ownership of a descendant listener. Never terminate any process by listener PID; that PID is only an observation. No HTTP call is used for ownership.

The Windows job driver can now accept explicit endpoint definitions and an injectable resolver; when configured it constructs the native resolver or accepts a fake test boundary. Its real Windows `health_ready` still returns false: no actual runtime READY path is claimed. The default coordinator remains unavailable and nothing is wired into `scripts/dev.ps1`.

Process exit/reuse between observations, port reassignment, IPv4/IPv6 bind behavior, scoped-address policy, duplicate records, Job Object inheritance and timing around HTTP requests retain TOCTOU uncertainty. The implementation and ctypes layouts/calling conventions require independent Windows review and actual native tests.
