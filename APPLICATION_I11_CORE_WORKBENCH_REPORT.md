## Changes

* A stream failure could leave a message's workflow marked planning or executing after the composer unlocked. The existing error callback now marks an active workflow interrupted, while retaining already failed/cancelled states. It does not claim that side effects were undone.
* Image chat uses the selected text model for its reasoning stage as well as a separate vision model. The composer now blocks an image when the selected text model is unavailable and explains why, even when multimodal capability itself appears available. Existing image type/size checks and preview cleanup remain unchanged.
* `chatDisabled` previously allowed unknown chat or image capability state. It now requires `available`; a configured or merely unknown model is not presented as usable. An operator may need to use the existing explicit model inventory check before sending; inventory is still not proof of successful inference.

These are targeted behavior and status-announcement changes; no broader accessibility or design claim is made. Existing account-keyed workbench remounting, server-owned conversations, logout handling and stale callback guards were retained. Stream/tool event matching still uses ordered tool names, not independent invocation IDs for every live call. The request “multiply that result by 3” has not been demonstrated to bind a prior turn's verified tool receipt and remains an integration gap. The basic arithmetic shortcut can answer a simple expression without claiming a tool ran. Other live-model routing quality is unknown.

## I11.1 — cross-turn result references

**I11.1: PARTIAL. Overall I11: PARTIAL.** Verified cross-turn calculation or conversion is **not implemented**. Within a planned task, verified result objects are available in `executed_step_results` and dependency binding requires `evidence_verified`. That list is local to a running task; task summaries and persisted `tool_events_v1` do not contain an independently verifiable typed value and execution receipt. The arithmetic shortcut can produce 42 without a task/tool receipt. Ordinary assistant provenance is process-local and applies to independent plain-chat content, not proof that a tool produced a numerical value. Persisted text, numbers and hashes therefore cannot safely supply the requested cross-turn reference.

As a narrow immediate safeguard, the actual chat route now identifies certain explicitly phrased prior-number operations before a provider or tool is invoked and returns `RESULT_REFERENCE_UNAVAILABLE` with a request to include the number and units. Streaming emits an error event without `done`; non-streaming returns 409. Existing session ownership is checked first. This **does not resolve references**, and it rejects these phrases even if an earlier task succeeded. It is deliberately a limited anchored pattern, not a comprehensive coreference detector: other wording may still reach the model, and nonnumeric uses of matched phrases may be rejected. Self-contained multi-step expressions are not blocked by this guard. No durable trust store, proof promotion, automatic replay, change to calculator authorization or new privileged route was added. An in-process test verifies error propagation and cross-owner denial; it does not establish coverage for all forms, units, cancellation, ambiguous or tampered results, restart, or account races.

## I11.2 — Process-local numeric follow-ups

**I11.2 passes for the scoped streaming workflow. Overall I11 remains PARTIAL. Production remains NO-GO.**

Simple arithmetic in streaming chat now uses a deterministic single-step plan through the existing plan validator, task manager, registry, dispatch authorization and tool verification. Supported follow-up phrases construct the same kind of plan from an immutable receipt. The model has no role in choosing the receipt or the resolved arguments. Receipt creation follows authoritative task completion and uses the typed tool output, checked again by the existing calculator or conversion verifier. Only the deterministic, single-step numeric path can issue a receipt. Assistant text, historical task summaries, model plans, and document or artifact outputs are ineligible.

The existing conversation memory owns the process-local receipt map. Each entry is keyed by server-issued conversation ID and binds the owner, conversation generation, completed task, invocation, assistant message, numeric value, optional unit and monotonic expiry. A receipt is usable for 15 minutes while its assistant message remains the immediately preceding message. The map retains at most 256 entries, refuses duplicate completion for the current task, and drops deleted conversations. A new memory instance starts empty. Lookup checks the current conversation binding and the agent checks the original task's ownership and completed status before planning and again before dispatch. Dispatch uses the existing I8.1 session and account refresh, registry version check, RBAC, clearance and approval controls.

The supported grammar covers multiply, divide, add, subtract and explicit from/to conversion. Arithmetic accepts unitless receipts. Conversion from a typed quantity requires the stated source unit to match the receipt. The converter checks dimensions and numeric bounds. Missing, stale, incompatible and ambiguous references ask for the number and units. Multiple-step plans have no declared final result and yield no eligible receipt. General coreference and non-streaming receipt execution remain outside this scope. Concurrency is checked against adjacent message IDs and receipt identity at the local dispatch boundary. Cross-process atomicity and independently protected persistence remain unverified.

The in-process production chat route exercised 42 → 126 → 131 → 126 → 63 → 63,000 m → 63 km using real calculator and conversion handlers and a fake provider fixture. Regressions exercised failed verification, interrupted execution before task completion, ambiguous multi-step results, intervening assistant prose, duplicate receipt replacement, expiry, mismatched units, dispatch authorization loss, conversation deletion, cross-owner and cross-conversation denial, and replacement of the memory instance. This does not simulate arbitrary writes to trusted process memory or a real OS process restart. The existing frontend receives verified result summaries and terminal errors through its current SSE contract.
