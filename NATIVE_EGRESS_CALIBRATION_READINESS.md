# Native egress calibration readiness

## Decision: BLOCKED

The current implementation is **not ready for a controlled native calibration**. The specific blockers are the absence of a reviewed, non-external calibration stimulus and correlation procedure; no native validation of event collection or audit restoration; no way to correlate the sanitized output to a particular PID or destination; unverified effective isolation and audit permissions; and no independently checked rollback snapshot. Network-sensitive application tests remain blocked. Production NO-GO.

This is a read-only source and report review. It did not access the VM, run the collector, change audit/firewall/network settings, execute tests, or build/sign an ISO. Earlier synthetic test results in `OFFLINE_EGRESS_MONITOR_FOUNDATION_VERIFICATION.md` are historical, not native verification. User-reported adapter isolation is useful context but was not rechecked.

## Findings against the requested checks

| Check | Evidence and decision |
| --- | --- |
| 1. Guest identity and permissions | `guest_wfp_monitor.ps1` requires a nonempty supplied GUID/name/snapshot label; compares CIM VirtualBox model, UUID and machine name; rejects adapters reporting `Up` except names containing `Loopback`; asks for typed `ISOLATED`. This does **not** independently inspect VirtualBox adapters, all host channels, snapshot existence, or prove the supplied identity is trusted. It has no explicit elevation/privilege preflight. Actual read/set rights for audit policy and access to Security log are unverified. Microsoft specifies audit-policy read/write permissions or `SeSecurityPrivilege`; administrator membership alone should not be treated as proof. [Auditpol get](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/auditpol-get), [auditpol set](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/auditpol-set). |
| 2. Audit modifications and restoration | `Inspect` queries the selected subcategory and firewall profile defaults without intentionally changing them. `Capture` requires a switch and typed approval; if failure auditing was absent it invokes `auditpol /set` for the **system** `Filtering Platform Connection` subcategory with `/failure:enable`. It does not intentionally change success auditing or firewall rules. It sets `$changed` before the native call and in `finally` calls the shared restoration helper to verify expected current state, disable only failure auditing and check equality with the prior state. This has injected success/conflict/failure tests only; native calls, localized output, Group Policy refresh, races and actual restoration have not been validated. A failed call may leave ambiguous state; termination or power loss can bypass `finally`. |
| 3. No durable export | Potentially usable for a **limited human-observed console experiment** if a reviewed procedure supplies trusted inputs and correlation separately; it emits sanitized structured 5157 lines, initial audit state and restoration status. It does not write durable reports, preserve initial policy outside process memory, report complete monitor health, or establish chain of custody. Photographing console output is possible but has not been validated as sufficient for this calibration. Durable export is disabled and its absence is not itself proof of unsafe network behavior; the missing observation/correlation and recovery evidence remain blockers. |
| 4. Event collection | `Capture` sleeps 1–60 seconds, then runs one `Get-WinEvent` query on Security ID 5157 with `StartTime` and `MaxEvents 500`; it is **not continuous polling**. `Get-WinEvent` returns newest events first by default; a 500-event cap can omit earlier ones. Log rotation, overwrites, event loss, start-time races, query and native-call deadlines, Security-log access and actual event XML are unverified. Parser validates selected fields, rejects duplicates/malformed records and redacts process, image and both addresses. It does not validate event-provider identity itself. It does not preserve PID, process creation time, destination or filter ID for independently correlating a stimulus. Synthetic XML tests cannot establish actual 5157 accuracy. [Get-WinEvent](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.diagnostics/get-winevent?view=powershell-7.5), [Microsoft event 5157](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-5157). |
| 5. All VM adapters disconnected | Possible in principle to investigate a separately designed local stimulus, but **not established** here. A non-loopback attempt can fail for lack of route before WFP; a loopback connection may be exempt from the relevant filtering. No approved stimulus, safe loopback rule, event match or no-route discrimination is implemented. The Python calibration helper is synthetic; `OBSERVED_BLOCK_ONLY` is not native coverage. Silence means UNKNOWN. |
| 6. No external exposure | A physically disconnected guest can reduce risk, but the guest adapter check alone cannot verify hypervisor state, alternate interfaces, virtual host channels, proxies or other escape paths. No reviewed stimulus exists to establish that it cannot contact anything external. The host is not touched by the script intentionally, but this does not independently prove host isolation. |
| 7. No firewall changes | The existing script does not modify firewall rules, though Capture may change guest audit policy. There is **no demonstrated no-rule-change stimulus** that produces an attributable WFP block on the existing VM. Do not assume loopback or a nonexistent route will produce 5157. A separately reviewed disposable fixture may need a narrowly scoped guest-only rule; that would require separate explicit approval and a new design, not a silent workaround. |
| 8. Rollback snapshot | A **separate approved, recoverable pre-instrumentation VM snapshot is required** for any capture changing audit settings; retain the existing baseline. The script accepts a label but does not verify snapshot creation, integrity or restore capability. Restoration after a passing capture is still recommended for the disposable environment; preserve evidence first. |
| 9. Failure or partial restoration | Stop all further tests; record or photograph sanitized error and original/current audit state where safely available; do not retry `auditpol` blindly or change host settings. Preserve evidence before the operator restores the explicitly reviewed pre-instrumentation snapshot; verify rollback afterward. The script emits `audit_restore_failed` and `RESTORATION UNCONFIRMED` on restoration error, but cannot guarantee console output or cleanup on a killed process. Treat audit-enable ambiguity, missing collection, output cap, parser errors, hung process, concurrent policy changes or lost evidence as UNKNOWN and snapshot-reversion-required. A hung native call is not forcibly bounded by the capture delay. |
| 10. Prerequisites | **Blocking**: no native verified collector/restoration; no approved non-external stimulus and observable PID/destination correlation; no verified hypervisor/guest policy and snapshot evidence; no safe separately reviewed transfer/signature chain for these new files. Logging calibration data and protecting sensitive event fields need a reviewed approach. No unprivileged application launch or `network_sensitive_test_runner.ps1` can change this: the latter is explicitly deny-only. |

## Minimum separate approvals

1. System owner approval for an identified disposable VM and a **new pre-instrumentation snapshot**, with an operator-controlled restore and evidence-retention procedure.
2. Security administrator approval for guest-only audit-policy inspection/modification, Security log access and the exact test process; verify effective rights and original state beforehand. No host changes are authorized.
3. Independent review and approval of the **specific** calibration mechanism and evidence-correlation design, including how it stays inside the guest, how WFP blocking is verified, which protocols/addresses are covered and whether a narrowly scoped guest firewall change would be needed. Do not alter rules merely to make the event appear.
4. Review of exact staged source and publisher/hash chain, bounded execution/timeout behavior, handling of sensitive event fields, log capacity and snapshot recovery. Approval for this limited calibration would not authorize Chroma, Ollama, FastAPI, the prior rejected full suite or production release.

## Shortest path to a future ready decision

First independently design and review a safe calibration stimulus and correlate an actual Windows event to its process and expected destination without disclosing sensitive data. Address event-loss/monitor-health and audit restoration evidence, including interrupted collection. Confirm the VM's hypervisor isolation, applicable Windows Home audit capability, security permissions and a separate rollback snapshot. Reassess whether console photographs suffice for the narrowly scoped calibration or a protected durable export is necessary. Then perform a new readiness review and obtain explicit approval; **there is no execution sequence authorized by this BLOCKED decision**. If the stimulus fails before WFP or no event is seen, record coverage UNKNOWN and stop.
