## Readiness and provider contract

- `GET /api/health/capabilities` reports configured and installed vision choices plus selected model evidence. `POST /api/health/capabilities/vision-check` requires `VIEW_DATA`. It checks the registry's `vision` capability, the current Ollama inventory and a provider-reported digest. The request goes to the configured plain HTTP loopback endpoint with proxies and redirects disabled.
- The probe creates a synthetic solid-color PNG in memory and asks for its color. It requires a matching model, a completed non-tool response and the correct color. The probe is bounded to 30 seconds and 16 KiB of response data. The image is generated by the readiness probe and does not come from the user's upload. This test exercises the image input path. It supplies no claim about general visual accuracy or independent weight attestation.
- Both readiness records are scoped to their model, capability, configured endpoint and observed inventory. Changes to the observed digest, model configuration, endpoint or inventory invalidate the matching check. Each proof expires within the earlier of the 60-second inference and inventory windows. The image route checks both before acceptance and at stream start, and rechecks the relevant proof before each provider stage. Ordinary text requests retain the existing readiness gate, including when submitted through the image endpoint without an attachment.
- The first stage sends base64 in the Ollama REST message's `images` array. The second stage receives the model-generated interpretation as user-role context and receives no image bytes. Existing provider checks reject mismatched model names, incomplete responses and native tool-call payloads. The image route buffers the reasoning answer before its text event, then emits one terminal success or failure. [Ollama vision API](https://docs.ollama.com/capabilities/vision) · [Chat API](https://docs.ollama.com/api/chat) · [Model inventory API](https://docs.ollama.com/api/tags)
- Maximum image size is 10 MiB or the lower server upload limit, with one extra MiB of aggregate form overhead. The existing decoder enforces one frame, limits each dimension to 8,192 and caps decoded area at 16 million pixels. Upload bytes are request-scoped. Multipart handling can temporarily spool to the OS temp directory and closes those resources. No image content, base64 data, filesystem path or download URL is persisted to conversation history. Only bounded descriptor fields are returned to the owner.
- Governance remains unchanged for protected RAG, OCR indexing, artifact publication, generated code, approvals, durable provenance and native process supervision. The two-stage public image workflow grants no tool permissions. AI image interpretation has no verified-result receipt.
