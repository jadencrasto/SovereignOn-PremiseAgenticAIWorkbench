## Backend identity and migration findings

The selected persistent client gets `persistent_durability_unverified`; an ordinary client, collection creation, or `count()` error selects `in_memory_fallback`. A `ChromaTelemetryConfigurationError` is re-raised, and directory creation errors are raised before the fallback `try`. In these failure cases construction aborts: the initial `initialization_failure` attribute is not exposed on a returned object. A fallback is therefore distinguishable from a selected persistent client, while callers must classify raised exceptions as initialization failures. Telemetry, collection and directory failures were exercised with stdlib fakes.

Identity uses `normcase(abspath(fspath(persist_dir)))` and a constant collection name. It is stable for equivalent lexical paths under the same working directory and Windows case normalization, but relative paths change meaning with the working directory; aliases, junctions, reparse points, file identity, replacement and independent writers are not resolved or authenticated. The nominal fallback identity still names configured Chroma storage, so it must always be interpreted together with `backend_status`. No status or path is proof of durable storage. The reserved `verified_persistent` label has no production issuer; even an injected label is rejected because `persistent_security_guarantees_available()` returns false.

The actual registry constructor was tested against a synthetic legacy SQLite table, twice: the original row remained PENDING with null verification fields. This covers the simple additive migration and idempotence, not concurrent migration, rollback, corruption or unusual historical schemas. Existing pending/revoked semantics are unchanged. The non-authorizing snapshot comparator is disconnected from startup and has no database writes. It cannot prove snapshot completeness or prevent cross-store races.

## Denial-boundary checks

The synthetic audit invokes the source bodies for retrieval, workspace file read, graph query, task approval, task resume, artifact preview/download, generated-code execution and document upload with fake dependencies. The selected paths returned empty/withheld data or raised a denial before touching the supplied sensitive stores, approval manager, executor or embedder. Task approval and both artifact routes were exercised with fake HTTP exceptions; task resume was exercised as an async generator. No OS process was launched. The underlying policies were loaded from the actual source files.

These are focused **function-body tests**, not FastAPI route, middleware, authentication, lifecycle, server, multiprocess or browser integration tests. Extracting functions through AST omits decorators and replaces default arguments; this avoids unreviewed framework and dependency initialization but cannot confirm routing configuration. Source inspection shows current calls to the document, task, artifact and execution gates; no general claim is made about every internal access path or unrelated process. `VectorStore.add_chunks`, maintenance APIs and the demo script's direct file copies remain accessible to trusted in-process code; the ingestion assertion applies to `DocumentService.ingest_document`, not to every possible writer.

This is a scoped not-run count, not the number of all tests excluded from the full suite. During harness development, an initial asyncio-based attempt was interrupted before a complete result after it reached event-loop creation; it had already displayed a test error, so no pass/fail total is asserted for that attempt. A subsequent complete development run had **6 passed and 1 error**: the test harness left synthetic SQLite connections open and Windows refused temporary-directory cleanup. The harness was corrected to close its connections, then the final 7/7 audit run passed; this was a harness error, not an application failure. A test-created empty `unused` directory could not be removed because Windows denied access; it was not an existing project file or VM evidence. The final test now uses a temporary directory instead. The failed development run may have left its temporary SQLite fixture in the system temporary area.

The scripts import standard-library modules and explicitly loaded source modules only; no pytest plugins, Chroma, Ollama, Docker or VM were started. The harness advances only coroutines that complete immediately and does not create an event loop. No independently enforced OS network boundary was established. `git diff --check` exited 0 with line-ending warnings; it does not validate untracked files.

## Files changed and remaining blockers

Only `tests/backend/test_batch2b3e1_offline_stdlib.py` and this report were added in this batch. No compatibility fix was applied to production: the identified ingestion change is intentional, and neither the older seed/evaluation reporting problem nor a route-level API redesign should be silently changed in an audit.

Blocking gaps include OS-level egress and denied-attempt monitoring, Windows handle/reparse safety, independent-writer exclusion, stable backend/collection identity, rollback protection, immutable model verification, actual cross-process recovery, real startup and framework integration, and regression coverage for the dormant pending-ingestion stages. The previous offline VM evidence is operational evidence, not authorization for this checkout. Reported route and denial observations do not authorize features.

Recommended next batch: update demo/evaluation reporting so denied ingestion cannot be reported as success, and design isolated synthetic fixtures for the dormant ingestion stages without any production bypass. In parallel specify and independently review the filesystem, writer-exclusion and cross-store freshness protocol before implementing persistent reconciliation. Keep all feature and production gates closed pending their separate evidence.
