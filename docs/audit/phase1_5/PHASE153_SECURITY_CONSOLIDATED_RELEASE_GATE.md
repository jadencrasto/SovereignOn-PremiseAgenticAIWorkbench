## Verified invariants and integration findings

* The current source returns false from `document_content_allowed()` and `task_content_revalidation_available()`. Their restrictive behavior is a deliberate compatibility loss, not evidence that source authorization or task provenance is solved. An ACTIVE or indexed-looking record must not be treated as an authorization decision.
* The current source creates PENDING records before exclusive file creation, binds upload ID and chunk manifest, and conditionally records readback. The vector client can fall back to an in-memory collection (`backend/rag/store.py`); an ordinary readback or configured directory does not establish durable storage. Source, vector store and SQLite are not one transaction. At startup `mark_restart_unverified()` marks records; it does **not** reopen sources, reconcile index contents or perform crash recovery.
* Application startup uses `active_settings` for the document service and shared task database registry (`backend/main.py`). Other global settings, direct service constructors and test-injected dependencies still require contract-by-contract review; no claim is made that every configuration path is unified. Tests using fakes cannot establish live initialization behavior.
* Conversation registry records do not establish trusted freshness after database replacement or rollback. Memory-driven lifecycle changes use cooperative locking, while direct registry calls may not. Stream checks limit observed revocation but cannot recall sent bytes or guarantee independent revocation cannot occur between check and emission. Session changes and clearance are not proven continuously reloaded during a request.
* Prior reports describing an artifact filename collision as open or an expected failure are historical. Subsequent artifact write-integrity work and the current synthetic collision guard show containment in the tested path, not a general proof across Windows reparse points, all legacy files or all artifact writers. Artifact viewing remains denied. Prior descriptions of startup reconciliation must be read with the more recent 2B.3C clarification above.
* Public error handling is not universal: `backend/api/artifacts.py` still contains `str(exc)` in preview/download handling. The current authorization guard blocks those paths; this is a **latent defect**, not a demonstrated currently reachable public disclosure. `backend/rag/service.py` logs upload names and internal paths at different log levels; log access/retention requires operational controls. No logs were changed.
* Document owner/clearance is bound from server request context in the integrated path, but context variables and internal methods are not a security boundary against compromised in-process code. SQLite/vector/filesystem rollback or independent writers and mutable local state cannot be solved merely by matching Chroma metadata.

## Minimum release sequence

1. Maintain all current deny controls; separately approve and provision a disposable, monitored, default-deny offline environment with no production data. Verify isolation independently before any real persistent Chroma or model use. This audit does not authorize the earlier rejected request or suite.
2. Prove persistent backend selection, immutable model identity where available, safe Windows file handling, exact manifest across an actual close/reopen and conservative interruption/revocation recovery. Explicitly address concurrency and rollback. Only then consider conditional document activation; ACTIVE alone must never authorize retrieval.
3. Implement a single source-revision authorization decision using current identity, owner, classification, revocation and generation, and integrate all document consumers. Demonstrate authorized and denied routes with synthetic tests and then independently approved operational tests.
4. Establish trustworthy transitive task provenance and authorized approval/resume without replay, then artifact identity/linked ownership and safe public presentation. Retain per-feature denial until independently verified. In parallel close conversation cross-process/freshness gaps and validate current clearance.
5. Review remaining output/error/log boundaries, compatibility, operational backup and restoration, browser and local-model workflows. Only then assess a feature-specific release; OS isolation and telemetry evidence remain separate operational gates.
