# Batch 2B.3F — Windows filesystem identity and writer-exclusion design

Date: 2026-11-12. Branch `phase1-5-recovery-security`. **Release decision: NO-GO.** This document is a proposed architecture, not a security implementation or authorization to release. No production paths, SQLite schema, authorization gates, VM, network settings, offline evidence or the `unused` reparse-point directory were changed. The only code added is `tests/backend/test_batch2b3f_protocol_model.py`, a standalone conceptual model.

## Existing implementation and assumptions

The 2B.3E reports and release gate remain controlling context. `VectorStore` uses a lexical absolute normalized-case path, attempts `PersistentClient`, calls `get_or_create_collection`, and can fall back to memory; it backfills legacy metadata. A client, path or same-process readback proves neither durability nor identity. `DocumentService` denies ingestion before reservation because `persistent_security_guarantees_available()` is false. Startup marks registry rows restart-unverified, but opens the current vector store before this step. `index_reconciliation.compare_snapshot` only compares caller-provided observations and never verifies/persists authority. `QuarantinedSources` uses pending/revoked rows; `immediate_transaction` protects a SQLite transaction only. Conversation registry coordination and context variables do not exclude external filesystem/Chroma writers. `_persist_new_upload` uses exclusive creation, digest and basic symlink/reparse checks but documents that Windows reparse resistance is unproven. Current code is not this design.

The operator-reported isolated VM write/reopen/restart checks concern a synthetic ChromaDB 1.5.9 environment; the network-attempt capture is unresolved. They do not establish application authorization, independent writer control, current installation identity or Windows filesystem guarantees. This batch did not inspect or modify original evidence.

## Threat model and trust boundary

In scope: accidental or concurrent FastAPI workers; independently launched maintenance and backup processes; SQLite, Chroma and source-file writers; process crashes; stale handles, retries and ambiguous commits; source/index/directory/database replacement and replay of an older valid backup. Paths and metadata supplied by clients or index entries are untrusted. Protected source contents must not be disclosed or executed. Administrators, service setup and an independently protected freshness witness are trusted only after explicit verification. A compromised OS kernel, local administrator, malicious storage driver, privileged backup/restore account, malicious service binary, or a writer with equivalent broker credentials may bypass local protections: detect where possible and otherwise retain unverified state. A path, timestamp, volume serial, file ID or SQLite counter alone is not an anti-rollback witness.

Proposed deployment boundary: one dedicated, restricted broker/service identity owns the source root, index root, SQLite DB including journal/WAL/SHM, coordination object and their parent directories. ACLs deny ordinary FastAPI workers and maintenance identities direct mutation, rename, delete, ACL/owner changes and alternate writable aliases. They make authenticated requests to the broker, which serializes every mutation and recovery operation. Existing open writable handles, mappings, inherited/duplicated handles, share modes, backup privileges and other brokers must be inventoried and eliminated before admitting the boundary. Maintenance/backup/restore is stopped or mediated by the same broker; operator and volume administration remain outside the guarantee. Multiple workers are clients, not simultaneous owners of independently opened Chroma stores. A cooperative byte-range lock is defense in depth, never the security boundary: a process with direct write access can ignore the lock file or use another namespace, and byte-range locks do not prevent mapped-file access.

## Windows handle and namespace protocol (design only)

1. Provision an approved local NTFS storage volume and roots under a protected ancestor; record its trusted identity and ACL policy out of band. Network shares, OneDrive/cloud files, unknown filesystems, mount transitions, unsupported filter drivers and roots whose ancestry cannot be authenticated are **unsupported** until independently reviewed. Existing roots are opened, not created, during recovery. Root bootstrap from an administrator-controlled anchor must itself avoid untrusted ancestor traversal; if this cannot be established, stop. Reject unexpected device names, UNC, drive-relative and absolute child names, `.`/`..`, separators in a single component, alternate data streams/colon and ambiguous Windows names.
2. Use a reviewed native broker, not `Path.resolve()`, `lstat()`, string prefix containment or `O_NOFOLLOW` alone. Acquire handles with appropriate minimum rights and `OPEN_EXISTING`; directory opens require `FILE_FLAG_BACKUP_SEMANTICS`. The final component can be opened with `FILE_FLAG_OPEN_REPARSE_POINT` and inspected using `GetFileInformationByHandleEx(FileAttributeTagInfo)`; reject reparse tags, including symlinks, junctions and mount points, rather than follow them. These flags alone do **not** prove that intermediate path components were not traversed. Microsoft documents handle-relative names for `NtCreateFile` and `OBJECT_ATTRIBUTES`' `RootDirectory`/`OBJ_DONT_REPARSE`; the exact supported user-mode combination and race behavior needs platform-specific review and adversarial testing before adoption. Traverse each component relative to an already validated directory handle, rejecting every reparse, or use another independently proven equivalent. If supported handle-relative no-reparse traversal cannot be established, fail closed instead of falling back to path reopening.
3. Keep validated root, ancestor and source handles alive across validation/use and obtain `FILE_ID_INFO` (volume serial plus 128-bit file ID) and file type/link count from the handles. Compare against the trusted source binding and read/hash **through the same source handle**; bind digest, byte count, source ID/revision and relevant metadata to the snapshot. Do not open a checked path again for content. File IDs can be reused after deletion and volume serials can be duplicated/restored: pair IDs with the live handle, protected generation and content digest, and never treat an ID seen after restart as uninterrupted continuity.
4. Reject files with link count other than one and reject a storage root or ancestors that have unexpected reparse/identity/ACL state. Link count is only an additional check: even link count one and a verified path do not eliminate aliases, later changes, prior mappings, or privileged modification without enforced directory and file ACLs. Hold appropriate share modes and handles to exclude conflicting write/delete/rename opens where compatible; acquisition failures or previously open incompatible handles fail closed. Validate that delete/rename rights via parents and pre-existing handles cannot defeat the intended restriction. Revalidate handle identities, digest, protected generation, and root/collection binding before commit; fail on any uncertainty or instability. Stable handles alone do not protect the contents from an already-open authorized writer.
5. Index store is a multi-file backend. Do not treat the parent directory handle as proof that Chroma accesses those exact files. Require a broker-owned adapter or supported handle-bound, read-only/immutable snapshot with a documented complete manifest and atomic snapshot semantics. If Chroma requires uncontrolled path-based reopening, can write during reads, or cannot expose the needed namespace/collection identity, the verified-recovery path is blocked. `get_collection` rather than `get_or_create_collection` is necessary but **not sufficient**: opening `PersistentClient` itself might initialize or mutate a path. Verify exact installed-version behavior independently; require an existing backend, database/tenant and immutable collection identifier and prove no creation, migration or network attempt, otherwise stop. Never delete unknown entries or reconstruct a missing collection during verification.

## Writer exclusion, lock hierarchy and fencing

All participating operations (ingest, registry updates, index writes, source changes, reconciliation, revocation, maintenance, backup/restore) go through the broker. Proposed hierarchy, always acquired in this order:

1. **Broker instance and trusted root admission:** exclusive service startup lease, protected object identity and ACL admission; fail if another active owner or unknown existing handles cannot be excluded. The lease is held for the broker lifetime, and cannot authorize fallback to a path-based local client.
2. **Store-wide maintenance/recovery lock:** held exclusively from begin through final cross-store verification and registry commit, including revalidation of the freshness witness; bounds all collection mutation and blocks maintenance. Ordinary operations must acquire the same lock in shared/exclusive mode according to a reviewed policy; simplest initial implementation uses exclusive mode for all. To avoid deadlocks, no caller holding a lower lock waits for a higher one.
3. **Source locks:** when an operation spans sources, acquire exclusive source locks in canonical opaque ID byte order. Locks are for coordination, not ACL replacement. Hold identity-pinned source/root handles for the operation.
4. **SQLite `BEGIN IMMEDIATE`:** acquire last, for bounded, short state/fencing compare-and-set transactions only; do not wait for any prior lock while a SQLite transaction is open. SQLite serializes cooperating SQLite writers for that database; it does not lock Chroma, file paths, or databases replaced outside its connections. Release SQLite transaction first, then source locks and global lock in reverse order.

Use broker-issued non-reusable operation IDs and monotonic generations, not PID, wall-clock lease, or a stale lockfile as ownership. Every mutation records intent and advances a durable source/index generation; conditional commit checks the operation token, expected row state, source revision, current generation and revocation under `BEGIN IMMEDIATE`. Token/generation must also be enforced by every storage mutation path; a database-only token cannot fence a bypassing Chroma or filesystem writer. Revocation is broker-serialized with the same hierarchy. A revocation requested while recovery owns the global lock queues or cancels recovery according to a documented bounded policy; once committed it increments the generation and must win every subsequent CAS. If an independent SQLite writer can revoke outside the protocol, the CAS detects a *committed* changed row, but cannot close a check-to-use window for unmediated external data writes. Revocation acknowledgement must not precede durable commit and must not claim already-released data was recalled.

If a holder dies, Windows releases its handle-based locks on handle closure; this is not evidence that the multi-store operation completed. `LockFileEx` and share modes are not a journal, and byte-range locks do not prevent mapped-view reads/writes. On broker recovery reacquire all locks, authenticate root and external witness, fence old operation IDs, mark interrupted operations RESTART_UNVERIFIED or RECOVERY_FAILED, and inspect durable intents; never delete a presumed stale lock file, grant a new owner based only on elapsed time, or assume abandoned means safe. If an old process/mapping cannot be excluded or lock identity may have been replaced, stop. Enforce bounded retries/timeouts and alert; do not recover automatically by breaking a lock.

## Freshness witness and rollback

A monotonic integer stored only in SQLite is rolled back along with SQLite. Proposed mandatory independent anti-rollback authority: an authenticated, append-only durable witness outside the backup/restore domain, with strictly monotonic sequence, deployment/volume/root identity, database incarnation, operation ID, manifest commitment and terminal state. It must be writable only by the broker through a protected interface and resistant to replay or clone by the attacker in scope. A second ordinary local file under the same administrative control is not sufficient. This authority is **not currently implemented or available**; offline/air-gapped operation requires a separately specified local hardware or independently administered mechanism, and unsupported cases remain unverified. A hardware counter alone does not authenticate all related content or resolve its crash ordering.

Candidate ordering: under the global lock establish the current authenticated witness head and DB incarnation; persist intent and expected predecessor in SQLite; durably append a witness intent; perform protected store observations/writes; durably append a witness commit binding operation ID, predecessor, source/index generations and manifest; conditionally commit the matching SQLite record; verify both committed heads before releasing. There is no atomic transaction across witness, SQLite, Chroma and filesystem. Any crash between steps, uncertain write/flush, witness ahead/behind, duplicate/divergent chain, restored DB/WAL/SHM, replacement or missing witness makes the operation unverified and requires a separately designed, reviewed repair or operator intervention. No automatic success is inferred from a matching counter. Preserve revocation across restore using the independent authority; if that cannot be proven, block all access. The detailed witness format, availability, durable-write behavior and safe recovery are unresolved design work.

## Conceptual state machine

These are **conceptual** recovery overlays, not new SQLite schema or an authorization model. The existing PENDING and REVOKED lifecycle remains authoritative; no migration is proposed.

| Transition | Required preconditions | Postcondition and failure behavior |
| --- | --- | --- |
| PENDING → RESTART_UNVERIFIED | Startup or loss of verified runtime/writer continuity; durable pending row exists. | Persist/derive unverified marker without changing PENDING; no access. Legacy/incomplete rows stay unverified. |
| RESTART_UNVERIFIED → RECONCILING | Trusted broker and witness, all locks, valid source owner/revision and known manifest, supported immutable existing backend/collection, safe live handles and trustworthy storage generations; register unique attempt with conditional pending/generation CAS. | RECONCILING is non-authorizing; exact observations and relevant generation/identity snapshot captured. Failure leaves unverified or RECOVERY_FAILED; no implicit resource creation. |
| RECONCILING → VERIFIED_UNAUTHORIZED | Complete consistent index namespace snapshot, source digest and revision match, exact unique chunk IDs/text hashes and metadata with no missing, extra, stale or unknown-owned entries; configured model ID, actual dimensions, collection and backend identities match; independently verified immutable model digest if claimed, otherwise explicitly unknown. Locks/handles remain held, witness valid, generation and revocation unchanged, final conditional transaction and durability protocol succeed. | Only records the observed index consistency and verification timestamp under that attested context. No ACTIVE state, retrieval, disclosure or task authorization. Unknown/unattributable collection entries prevent verification unless a reviewed ownership and complete-enumeration scheme proves they cannot belong to the source. |
| Any non-REVOKED → REVOKED | Valid current revocation authority; serialize using broker/lock order; commit revocation and advance generation/witness under reviewed crash protocol. | Terminal for the source revision; interruption or unknown completion remains denied. Revocation cannot be overwritten by reconciliation. Cleanup is a separate authorized operation. |
| RECONCILING → RECOVERY_FAILED | Mismatch, error, timeout, unsupported API, witness discrepancy, loss of lock/handle, uncertain durable commit, or unexpected backend result. | Fail closed, retain evidence without sensitive disclosure; no deletion or authorization. A new attempt requires fresh admission and a new token. |
| RECONCILING / VERIFIED_UNAUTHORIZED → RESTART_UNVERIFIED | Process/host restart or loss of asserted lock, witness, source/index identity or freshness. | Drop prior live verification; never infer successful prior commit. REVOKED remains REVOKED. |
| RECOVERY_FAILED → RECONCILING | Underlying issue separately resolved; all entry preconditions re-established under a new operation/token. | Re-run entire observation; no trust from previous partial results. Unknown states fail closed. |

Document permissions, owner/current clearance, revocation, source revision, task dependency provenance and consumer-specific policy require separate explicit checks even if a future index reaches VERIFIED_UNAUTHORIZED. Current `document_content_allowed()` and all other gates remain false/denied.

## Required independent OS verification and roadmap

1. Review broker threat model, service-account ACLs/privileges, process isolation, backup/restore duties, pre-existing handles/mappings and exact supported Windows/filesystem versions. Verify service impersonation, handle inheritance/duplication and no unmediated writers. A cooperative lock alone is unacceptable.
2. Design and independently review a native handle-relative implementation and bootstrap protocol. On a separately approved disposable isolated machine, test nested junctions/symlinks/mounts, name aliases, hardlinks, streams, parent replacement, rename/delete/share races, pre-existing writable handles, mappings and privilege bypass, plus file-ID reuse and unsupported filesystems. User-mode API documentation gaps are blockers, not assumptions.
3. Establish a version-pinned Chroma read-only/existing-collection and complete-snapshot contract, including independent process writers, collection identity, backing file reopening and no telemetry. Current official documentation describes `PersistentClient` as intended for local development/testing; production suitability requires a separate supported architecture assessment. The earlier VM verification does not satisfy this contract.
4. Specify and prototype an independent anti-rollback witness, generation/fencing, crash ordering and revocation/restore protocol. Model every crash point and test process kills, concurrent writers, stale tokens, witness loss, database/volume rollback and recovery under a verified boundary. If external attestation or strong single-owner controls are unavailable, leave recovery unverified.
5. Only after independent review implement isolated non-authorizing recovery, then separately review per-consumer authorization and end-to-end release gates. Do not activate features from manifest equality.
