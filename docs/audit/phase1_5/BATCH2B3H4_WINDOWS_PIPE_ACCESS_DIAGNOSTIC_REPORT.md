## Root-cause assessment and rights

**Strong hypothesis, not a conclusively isolated root cause:** both processes run in an AppContainer, while the pipe DACL has only a traditional user-SID allow ACE and no AppContainer package/capability SID. Microsoft documents a dual-principal AppContainer access model requiring both the user/group and AppContainer portions to be granted access. The matching user SID and generic masks therefore do not establish effective access. Microsoft also documents an AppContainer `\\.\pipe\LOCAL\` namespace requirement in the named-pipe API documentation; the draft uses a different name. These facts make AppContainer access control and namespace compatibility concrete, plausible explanations for error 5, rather than merely guessing that a generic sandbox caused it.

The exact denied check is still unknown: no `AccessCheck`/`AuthzAccessCheck` with complete object-specific generic mapping and both token principals, independently inspected package SID/capabilities, event trace, or controlled comparison with the same policy in an independently provisioned environment was performed. AppContainer namespace handling, package/capability identity, object namespace virtualization, endpoint DACL, and other managed-environment policy remain competing or interacting hypotheses. The initial H.3 cross-tool-session error 2 and same-command error 5 are different observations and cannot prove namespace equivalence. No DACL or namespace was changed merely to test a bypass, no `Everyone` ACE was added, and no functional retest was run after a guessed change.

There is a separate least-privilege defect in the draft's chosen rights: Microsoft documents that `FILE_GENERIC_WRITE` includes the bit also used for `FILE_CREATE_PIPE_INSTANCE`. An allow ACE for generic write may therefore grant more than writing messages, subject to the remaining security and instance checks. Before any future listener is enabled, design and test the smallest explicit access mask, server create-instance rights, and descriptor policy together. This is not asserted to be the cause of error 5, so this batch does not guess at an access-mask correction.

## I/O lifecycle review

The draft is not safe to enable on current evidence:

- It creates a fresh manual-reset event/`OVERLAPPED` for each operation and attempts to hold them during pending I/O. The behavior and lengths returned by pywin32 for both immediate and pending completion, including `ERROR_MORE_DATA`, have not been verified on a live connection. `_write` does not check the resulting byte count.
- A timeout requests same-thread `CancelIo`, then waits for a signal before releasing state; on failed cancellation or a non-signaled event it terminates the process. Cancellation does not itself prove completion, and no live test verifies all completion races. An unexpected exception or `KeyboardInterrupt` while an operation is pending can reach the `finally` that closes the event without a demonstrated cancellation/drain. Buffer and `OVERLAPPED` lifetime in those paths is not proven.
- If a connection completes during timeout/cancellation, `connected` may remain false and cleanup/`DisconnectNamedPipe` behavior is unverified. Client disconnect, message-mode partial reads, response consumption before server disconnect, sequential reconnection, first-instance collision, active-request shutdown and restart were not exercised.
- Parser limits are 1,024 request bytes and 2,048 response bytes, but end-to-end pipe framing and oversized-message behavior are not established. `CreateFile` and shutdown bounds are not demonstrated. The private draft's use of `os._exit` in unresolved cancellation is not an independently verified cleanup protocol.

For these reasons **no minimal production or draft transport fix was applied**; public `serve()` and `request()` continue to raise. No actual development ping was exchanged.
