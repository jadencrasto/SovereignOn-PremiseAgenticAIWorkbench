## Identity and administration

Existing `AuthStore` owns SQLite users/sessions; `get_current_user` resolves server sessions and rechecks active status; role and clearance checks and tool policies remain server-side. Actual roles are `viewer`, `operator`, `admin`: viewer has `VIEW_DATA`; operator additionally has read/write tool request, task/approval and `VIEW_SECURITY` permissions; admin additionally has user/config management. These permissions are not guarantees of successful execution: provenance, ownership, approval and capability gates still apply. `manager` and `user` are UI aliases, not valid roles. Unknown roles fail permission checks. Document clearance is server-derived and bounded by role.

Existing admin-only account list/create/update routes and session code were inspected; no new account modification operation was added. Existing updates lack a demonstrated compare-and-swap security decision, durable mandatory audit, complete session revocation on changes, and concurrency/race evidence. These routes are **not established as safe organizational administration** by this work. Disabling an account causes subsequent authenticated identity resolution to reject it; in-flight work and complete session invalidation remain unverified. Current audit writes can fail without failing the action and the user-update audit does not establish a complete actor/target, before/after and durable transaction history. Do not infer a trustworthy admin change history.

Added authenticated `GET /api/auth/me/permissions`, deriving boolean role permissions from the existing permission table. It reports role permissions, not effective permission to complete an operation or approval/provenance proof. Replaced the role portal's locally fabricated users, account creation and revocation success messages with this read-only response and existing server capability states. Unknown capability stays unknown; account switching discards stale permission responses. No user management write UI was introduced. Tests directly exercise the handler and authorization dependencies; no actual mounted UI or full authentication HTTP path was tested.

`get_current_user` now rejects disabled authentication for both `production` and `prod` even if the development override is set. This aligns the request guard with existing startup validation rather than relying solely on startup. Non-production unauthenticated development still provides a synthetic local admin; it is not organizational identity. Existing external-binding validation requires authentication and forbids development override, but does not establish network isolation. No organizational or Protected mode is asserted.

## Audit and configuration

Audit endpoints expose SQLite audit events and summary under `VIEW_SECURITY` (operator and admin); pruning requires admin. Pagination has a maximum of 200 and SQL filters are parameterized. The UI currently exposes raw event metadata and failure details: sanitization is a denylist and cannot prove all sensitive content is excluded. Audit records are best-effort, not independently protected against modification or rollback; ordinary application logs are not equivalent to security audit. A bounded synthetic audit filter and role check passed, but HTTP pagination validation, all denials and real audit durability remain unverified. Operational exposure needs a reviewed safe-field/provenance policy before organizational deployment.

Config validation now treats wildcard CORS as invalid for the `prod` alias too, rejects malformed Ollama endpoints, credentials, unsupported paths/query/fragment and invalid ports, and avoids echoing endpoint credentials, CORS values or directory exceptions. A loopback label indicates configuration only, not live availability or isolation; non-loopback gets a warning, not an offline guarantee. Validation's existing `ensure_dirs` creates directories and does not independently verify secure storage or write permissions. No runtime configuration editor was added. Models, storage identities and dependency readiness are not fully validated by these changes.
