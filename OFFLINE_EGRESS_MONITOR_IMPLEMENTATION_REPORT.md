## Implemented files

- `tools/offline_verification/guest_wfp_monitor.ps1`: explicit `Inspect` (default) and bounded `Capture` modes. Checks supplied nonempty VM UUID/name, VirtualBox CIM model, no active non-loopback adapters, snapshot reference and per-run operator statement. Inspection reports selected current audit policy and firewall profiles. Capture additionally requires the explicit switch and typed confirmation, enables only failure auditing for the **Filtering Platform Connection** audit subcategory when needed, reads a maximum of 500 Security 5157 events and displays a sanitized summary; it attempts to restore the original failure audit flag in `finally`, checks for conflicting audit state and reports restoration failures. It never changes firewall rules, runs tests or opens sockets. Retain snapshot rollback even after reported restoration.
- `tools/offline_verification/egress_monitor_core.py`: bounded stdlib-only synthetic XML 5157 parser; requires attribution, correct event, timestamp, addresses, ports, protocol and direction, strips process ID and image path from returned output. `calibration_decision` is a synthetic comparison helper, and `execution_gate` never grants more than `READY_FOR_REVIEW_ONLY`; it is not connected to a test launcher and does not confer authorization.
- `tools/offline_verification/test_egress_monitor_core.py`: synthetic event, malformed/missing attribution, gate and calibration tests. No live Windows events or audit policy calls.

The PowerShell collector and Python parser are separate: the collector displays an intentionally restricted, redacted console summary; the parser is not currently wired to actual Security event retrieval or an export pipeline. The PowerShell summary validates presence of PID/image and extracts protocol and source/destination ports, but redacts paths, IDs and addresses and does not establish durable process attribution. The Python parsed representation retains IP addresses and ports; sanitize further before sharing and protect local evidence. Neither component records process creation time, process ancestry, event-log loss or reliable monitor health, and neither proves external enforcement. The output of the real monitor always says `coverage=UNKNOWN`.

## Configuration prerequisites and exact proposed commands

These are **not authorization or instructions to run on the normal host**. A separate operator approval is required for an independently approved disposable VirtualBox VM, a fresh pre-instrumentation snapshot, guest audit changes, monitoring, evidence retention and any separate firewall-policy work. The VM model/name/UUID and adapter checks are mistake guards, not cryptographic proof of VM isolation. Snapshot reference and typed `ISOLATED` confirmation are operator attestations, not automatic proof of snapshot existence, recoverability or disabled hypervisor channels. Independently check all adapters absent/disconnected, no shared folders, clipboard, drag-and-drop or USB, no external paths/proxies, and suitable Windows Security log permissions/capacity. Inspect effective firewall policy and local WFP provider/rule exceptions with a separately reviewed procedure. This script reports profile defaults only and does not establish default-deny effectiveness. Its audit parser supports English output only and fails closed on other formats. Avoid running while another administrator or policy can change audit configuration; concurrent changes can still race the read/set/restore sequence.

Once the above has separate approval and package transfer/signature checks, proposed guest-only inspection is:

```powershell
.\guest_wfp_monitor.ps1 -Mode Inspect -ExpectedVmUuid <reviewed-uuid> -ExpectedComputerName <reviewed-name> -SnapshotReference <reviewed-snapshot>
```

For separately approved guest-only failure auditing, `-Mode Capture -ApproveGuestAuditChange` and an operator's `ENABLE GUEST AUDIT` confirmation are required. The 1–60 second window launches no stimulus. Capture uses `auditpol /set ... /failure:enable` only if failure auditing was initially absent. On normal completion it returns only that failure setting to its previous state and verifies the selected subcategory. Native calls can fail, a process kill can prevent `finally`, policy may be overwritten externally, and initial state may change between checks. In any such case preserve evidence and restore the independently reviewed VM snapshot. Inspect mode does not change audit settings. Capture reads at most 500 events and reports the cap as unknown coverage. No full-event-log backup, firewall modification or automatic restoration of unrelated settings is performed.

## Calibration and execution gates

**No automatic calibration stimulus is implemented or approved.** A disconnected VM can fail routing before WFP and generate no 5157. A separately approved design must first demonstrate an isolated, harmless stimulus with a provably non-external path and process identity, and confirm that the exact attempt is actually blocked by WFP and represented by 5157. A listener, default-deny policy, loopback exceptions or routing change must not be guessed or installed on the host. The existing synthetic helper accepts a matching event only as `OBSERVED_BLOCK_ONLY`; it cannot prove the real collector or OS recorded it. Missing event, wrong PID/destination/direction, early local failure, collector failure or unknown process coverage yields UNKNOWN. A passing sentinel covers only its actual path and protocol, not every process, packet, DNS resolution or loopback flow.

Network-sensitive tests must remain blocked until independent VM isolation, effective default-deny policy, approved guest changes, actual per-path calibration, verified rollback snapshot and healthy evidence collection have all been established. The helper models these requirements, but **there is no enforcement integration with the existing test runner**; do not interpret its booleans as OS evidence. The already documented unknown outbound request must not be retried. Network/firewall permissions require separate approval.
