# Post-Lifecycle security verification audit

**Decision: production NO-GO.** The user reports that the isolated Windows 10 Home VM passed the Lifecycle Service and synthetic Recovery suites, elevated preflight and development-signed package checks, with no snapshot reversion required after those passing runs. This audit did not inspect the VM, original console logs, exact ISO hash or snapshot inventory; these are operator-reported results, not independently authenticated evidence. The completed tests exercise a development service and synthetic recovery fixtures. They do not establish protected storage, actual application recovery, or production authorization.

The repository contains useful deny controls and prototypes, but the actual protected service, client authentication and OS storage boundary remain unverified; document, task, artifact and code workflows remain deliberately unavailable. The most important unresolved operational finding is the unidentified outbound attempt that caused automatic rejection of the earlier full-suite run. Its destination and initiator are unknown. No test was run in this audit, and the rejected suite must not be retried without separately approved isolation and monitoring.

## Counting and evidence conventions

The matrix groups the remaining scope into **15 distinct requirement groups**. Of these, **11 include a Windows VM or equivalent isolated native environment**, **14 have some safe host-testable component after dependency review**, and **11 require independent organizational review or verification**. These are overlapping counts, not 35 separate tasks. Host-testable does not mean that a complete group can be closed on the host; tests must be selected and reviewed individually with external plugin autoload disabled, no real network-capable dependencies or native initialization unless an independently effective network boundary is established. The Windows VM column identifies native evidence required for the proposed Windows deployment, not a claim that every feature needs that particular VM. Rows marked independent concern final acceptance even where development evidence can be gathered first.

Status: **A** completed within the stated scope; **B** implemented but native/operational evidence missing; **C** partial; **D** missing; **E** requires independent organizational assurance. A row can contain more than one status because a prototype and a deployment are distinct deliverables. Severity reflects the risk if the missing gate is bypassed, not proof of a present exploit; all denied features remain denied.

## Protected-profile VM work and actual prerequisites

Lifecycle uses a fixed-name **LocalService** fixture. K uses the same fixed service name with a separately provisioned restricted identity and observation-only endpoint. Lifecycle approval is not Protected approval. Use a separately approved protected VM configuration or snapshot, and verify the existing service is absent before provisioning; do not overwrite a service or reuse the Lifecycle fixture as protected evidence. Retain the clean and reusable snapshots the operator says remain. VM and snapshot markers prevent mistakes; they do not prove disposability or restore correctness.

The code in `tests/backend/run_batch2b3lm_native_inspection.ps1` checks an independently pinned manifest and returns observations with `authority=false`. `run_batch2b3k_protected_fixture.ps1` observes the already-running protected fixture or checks denial for a genuinely distinct identity. `run_batch2b3n_native_access.ps1` checks fixed synthetic objects for application, independent and broker roles. Its broker write exercise requires an **actual restricted service token** and an independently approved mechanism to run the probe under that token; an interactive copy of the broker account is insufficient. The K fixture does not supply such a probe host. Its single connection and finite lifetime mean another observation needs restart; continuous endpoint ownership and native request dispatch are not implemented.

Before any Protected tests, independently review and approve: dedicated logon identity and restricted service SID, protected executable and configuration, SCM and pipe descriptors, expected manifest digest, distinct observer/independent accounts, synthetic NTFS ACLs, actual token-query rights, and rollback procedure. Windows 10 Home may lack convenient local policy/account administration tools or needed provisioning capabilities; availability and required rights are not established. Do not work around this with broader ACLs, administrator-only observations or same-account substitutes. A separately provisioned VM may be more efficient if Home cannot support the reviewed setup.

Native verification should then cover token and restricted SID, service binary/configuration, endpoint binding and actual DACL, unauthorized distinct identity and squatting, application/independent direct create/write/delete denial, broker synthetic rights, parent and WAL/SHM fixture permissions, interruption, revocation and cleanup. Missing tooling for independently controlled concurrent writers, inherited handles, backup privileges and witness immutability must be implemented and reviewed first. Avoid repeated service installs or ISO rebuilds by agreeing on the full fixture and evidence capture before a single controlled execution; preserve separate per-run approval and snapshot rollback.

## What can be examined on the host

Read source and existing reports first. Review pure standard-library ingestion/reconciliation/denial tests such as `test_batch2b3e_offline_stdlib.py`, `test_batch2b3e1_offline_stdlib.py`, and `test_batch2b3e2_offline_stdlib.py` before selecting them. The prior gate reports 114 passed and 2 skipped in a broader synthetic selection; the offline package reports 60 passed and 1 skipped after artifact error hardening. These are historical results, not a new run. PowerShell mock harnesses and .NET self-tests can test logic after confirming they avoid native initialization, privileges, network and persistent production paths. A Python socket guard does not constrain native egress. Do not run unknown dependencies or the previously rejected full suite without an independently verified boundary.

Backend source still gates ingestion, retrieval, document listing/detail and generated code. Task, workspace, graph and artifact boundaries require targeted route/tool checks as well as source inspection; deny-by-default is containment, not a complete authorization implementation. Audit logging must be assessed for sensitive names, paths, error details, access controls and retention; current structured prototype diagnostics are not proof of tamper-evident organizational audit logging. Dependency and browser egress must be observed independently; static Chroma telemetry settings do not govern native SDKs or the OS.

## Optimized work order and completion criteria

1. **Preserve evidence:** record the operator's passing suite outputs, date, exact ISO/launcher and binary hashes, VM build and snapshot references without changing the VM. Mark them operator-reported until reviewed; record exactly which cleanup was observed.
2. **Close host-reviewable gaps first:** review gates, current source changes, safe dependency imports, emitter inventory and targeted synthetic test selection; run only demonstrably offline-safe checks. Resolve concrete findings in separately authorized implementation batches while maintaining all denials.
3. **Resolve egress observability:** independently approve and verify a default-deny, monitored environment; establish how attempted connections by native libraries and child processes are captured, including startup and missing-model paths. Do not re-run the rejected suite just to identify its source.
4. **Design and review one Protected fixture:** decide whether Windows 10 Home can satisfy the independent identities, token-query and ACL requirements. Provision only in a separately approved disposable snapshot; bundle mutually compatible tests before another signed package is built. Obtain genuine different-SID observations, service and endpoint evidence, and synthetic ACL-denial evidence with documented cleanup.
5. **Complete architecture before feature enablement:** enforce independent writer exclusion and filesystem identity; implement a separately administered freshness witness and conservative recovery; then implement document authorization, task provenance, artifact controls and any sandbox one boundary at a time with negative/positive and adversarial tests. Test actual deployment and restore behavior; do not grant access on an index or native observation match.
6. **Independent final gate:** an accountable reviewer verifies source/build provenance, test evidence, isolation, operational recovery, access controls, residual risk and change approval. Review each feature separately; native development PASS is not a production release decision.

Completion requires documented passing results for each applicable row, traceable artifacts and configurations, addressed skipped tests and limitations, and independent sign-off. A denied feature may remain disabled while another is reviewed, but the overall production security gate remains **NO-GO** until separately justified.
