# I9 document trust foundations

**I9: PARTIAL. Production RAG: BLOCKED; production remains NO-GO.** The changes close a misleading production API response and strengthen non-authorizing diagnostic contracts. They do not establish trusted document access or source freshness.

## Architecture and identity

Upload requires the existing write permission and server-derived clearance, then calls `DocumentService.ingest_document`; that service refuses to reserve or write unless the persistent-index security gate succeeds. The existing quarantined SQLite source registry reserves a server-issued `doc_v1_` ID, owner, classification, source digest and revision 1; manifest rows identify chunks and their text digests. Its only lifecycle states are pending and revoked, and `retrieval_eligible` always returns false. Parser, chunker, embedding service, Chroma-backed store and retriever exist, but the gated positive path lacks an authoritative owner/revision check. `document_content_allowed()` is always false, so retriever, vector reads, document detail and search cannot disclose content. Delete uses existing quarantine and storage restrictions; it is not evidence of secure deletion. No tenant model was added.

An ID, digest, matching index model string, or `match_unverified` diagnostic is not proof of ownership, live source integrity, an authorized revision, a verified embedding or an independent storage snapshot. There is no established production retrieval-authorized state, verified persistent index, durable audit/rollback protection, or safe promotion from pending. Existing internal grounding helpers are not connected to production retrieval.

## Changes

* `GET /api/documents` previously returned HTTP success with an empty list when document content was blocked. It now returns the existing `DOCUMENT_UNAVAILABLE` error with HTTP 503 before reading the store. Detail remains withheld; this does not enable retrieval or upload.
* The existing non-authorizing `compare_snapshot` diagnostic now rejects chunk IDs not bound to the source ID and index, boolean/non-integer revision and index metadata, and nonnumeric, boolean or nonfinite embedding values. An otherwise matching snapshot still reports only `match_unverified`; its source/chunk digests do not validate the semantic correctness of an embedding. Legacy noncanonical synthetic fixtures were updated to match the actual chunker contract.
* The isolated grounding helper now requires an explicit boolean scope decision: `False` filters a candidate; unknown or other truthy values fail rather than authorizing it. Context construction and answer validation require `True` again. The injected callback is a test interface, not current production authority.

## Synthetic evidence and outstanding gates

Temporary SQLite tests reserve a pending owner-scoped source, deny another owner, compare source bytes and chunk metadata, reject replacement, missing chunks, malformed vectors/IDs and revoked records, and retain `retrieval_eligible=False`. A separate synthetic grounding test preserves chunk and revision in citations and rejects indeterminate scope. Existing fake-provider grounding tests exercise citation dependencies and revocation during generation. These tests do **not** register an authorized retrievable source, verify real owner access through production search, connect citations to the source registry, validate persistent embeddings, or test real Chroma. In particular, a simulated callback is not production authorization, and the compared index snapshot is caller-supplied and untrusted.

Production ingestion remains blocked by `DocumentService` plus `persistent_security_guarantees_available()`; retrieval is blocked by `document_content_allowed()` across the retriever, store, document service and search tool. Before any gate change, independently establish filesystem identity and exclusive writers, current owner/session/clearance decisions for each source, revision-bound chunks and model identity, index readback and consistency, revocation and safe recovery across crashes, rollback resistance and document-derived assistant provenance. Each needs isolated cross-process, restart, corruption and authorization tests against the actual protected backend. No current comparison establishes these prerequisites. UI tests only verify blocked/unknown presentation and withheld sources.
