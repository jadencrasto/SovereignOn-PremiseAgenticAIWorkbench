# R6.6 — Frontend terminal-event contract

**R6.6: PARTIAL. Frontend runtime: NOT VERIFIED. Production: NO-GO.** Starting branch `main`, HEAD `2b96fee1f24777247f4efb7a18293eef4275e9cb`. Existing uncommitted work was preserved.

For ordinary chat, a successfully exhausted engine stream is followed by `done`; provider exceptions yield `error`. Planning and tracked-tool wrappers return on `task_failed`/`task_cancelled` and do not intentionally emit a subsequent `done`. Successful task completion can precede final text and `done`. An `approval_required` event can precede `done` while approval remains pending: therefore `done` marks completion of that stream, not necessarily completion or success of the underlying task. Local stop aborts client reception; it does not establish server cancellation or roll back tool effects. An EOF without a terminal event results in an interrupted-stream error in the client.

**Backend exception:** `_stream_denied_approval` in `backend/api/chat.py` actually yields `error` followed by `done`; `_stream_intercepted_approval` returns on `error` but can forward task lifecycle events before its unconditional `done`. These approval-interception paths do not uniformly follow the planning wrapper's terminal-event convention. They were not changed in this fixture-focused task; blocked approval resume remains blocked. The client parser treats the first `error`, `task_failed`, `task_cancelled` or `done` as terminal, ignores subsequent events and cancels the reader. This is a source-level observation, not runtime proof.

`frontend/src/api/client.ts` handles both JSON and multipart streams with terminal flags; `guardChatCallbacks` and the stream controller suppress callbacks after abort/switch. `ChatView` sets failed/cancelled state and stops loading. Account changes key the provider by principal and cleanup aborts the current controller, but full mounted logout/session behavior is not verified. A frontend callback invoked directly after terminal state can mutate state because that harness bypasses the parser; the defense against malformed SSE is the parser, not an independently terminal-aware callback. No automatic retry is passed from `ChatView` to `MessageList`; the new tool-result-then-error fixture checks that property. Neither a failed transport nor client abort proves that a tool had no side effects.
