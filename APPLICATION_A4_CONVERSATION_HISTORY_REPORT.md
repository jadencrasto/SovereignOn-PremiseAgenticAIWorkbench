# A4.1 conversation history and persistence — PARTIAL

Date: 2026-11-13. Production remains NO-GO; A1–A3 remain PARTIAL. Existing uncommitted work was preserved.

## Architecture and changes

Reused the existing atomic JSON `ConversationMemory`, SQLite `ConversationRegistry`, authenticated chat routes, provenance checks and React history sidebar. No second conversation database or data migration was added. New records carry creation/update timestamps; old records without those fields remain readable only where their existing authorization permits. JSON loading now rejects malformed message structures and duplicate message IDs rather than silently accepting them. Atomic replacement remains subject to the existing storage and filesystem limitations.

`POST /api/chat/sessions` creates a server-generated UUID and binds it to the authenticated server-derived owner. Sending without a session ID still creates a server-generated conversation; supplying an ID now requires an existing authorized conversation in both text and multimodal chat. This intentionally changes the legacy behavior that allowed clients to choose IDs for new conversations. Existing list, read, title and delete APIs remain in use. Missing and other-owner deletion responses are indistinguishable. A conversation with an owner label but no matching active generation binding is now withheld; the previous regression expectation allowing such legacy records was updated to assert denial. No automatic legacy migration or reassignment was added.

The application checks for an existing history file and a missing security database before `AuthStore` can initialize the shared database. Registry reads use read-only SQLite connections; registry lifecycle writes use SQLite `mode=rw` so a missing database is not silently recreated during use. Existing history without an active registry binding is not promoted. These checks do not provide an independent rollback/freshness witness, prevent every possible storage race, or reconstruct missing security state.

The frontend creates a server-owned conversation when the first message is sent, and treats a new empty chat as a local draft until then. It stores only the selected opaque ID in per-user session storage and re-fetches the authorized record on restoration. It refreshes the sidebar after creation, completion and deletion; deduplicates server IDs; skips records deleted during loading; shows loading/errors; confirms individual deletion; updates the active title after server-confirmed rename; and guards stale creation/stream responses. Selection and export revalidate access. Search is limited to titles so stale cached message content is not searchable. Withheld responses are clearly labelled and their content, sources, tool details, timestamps and copy control are not presented; sidebar message counts were removed. An abandoned create request may leave an empty server conversation, and stale client cancellation is not proof that a backend operation stopped.

## Provenance and remaining limitations

Persisting a record, displaying a message and replaying a message to a model remain separate decisions. Process-local assistant proofs are not persisted, so eligible responses from a previous process remain withheld after restart. Unknown, document-derived and tool-derived assistant content is not promoted; no protected key, independent freshness authority or rollback-resistant receipt was introduced. Data from unbound legacy records remains unavailable pending an authorized recovery mechanism. The lifecycle change requiring server-issued IDs may require older API clients to create a session first.

A4.1 and overall A4 are **PARTIAL**: mounted-browser verification, full application restart/recovery, concurrent multi-process and crash/power-loss cases, safe durable assistant replay, and independently protected freshness remain incomplete. The scoped tests do not establish production readiness. No launcher, real application, Ollama, Chroma, VM, security-policy change, commit, merge or push was used. Recommended next action: validate the history UI in an authorized offline React DOM/browser environment and separately design recovery for unbound legacy records and trusted durable provenance without weakening existing gates.
